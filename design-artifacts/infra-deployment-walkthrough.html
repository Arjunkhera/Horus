Horus Phase 2 · Section D · Deployment & Bootstrap

How Horus Runs in the Cloud — a Visual Walkthrough

Written for someone who has not used Kubernetes, Helm, or ArgoCD before. By the end you'll understand what each piece does and how the two-service control plane (horus-service + operator-service, ADR-0004) maps to the K8s objects that run it. Updated 2026-05-28.

0The mental model in one breath

There are two places Horus runs, and they are very different.

① On each user's machine (the Client)

NPM CLI (@arkhera/horus) + 4 Docker containers: horus-ui (port 8400, formerly reader-server), anvil, typesense, neo4j. Anvil is LOCAL and git-synced. Vault + Forge are REMOTE. Federation is client-side: horus-ui-client merges local Anvil results and remote results from horus-service in the browser.

② In a shared cluster (the Control Plane)

One Kubernetes cluster per company, running the remote services (Vault, Forge, user management, routing). Two control-plane services (ADR-0004): horus-service (public ingress — identity + aggregation) and operator-service (admin ClusterIP only). This is Section D — what this page is about.

Analogy. The Client is like the app on your phone. The Control Plane is like the company's servers the app talks to. You install the app once per device; the servers run once for everyone.

1The words, in plain English

Kubernetes (K8s)
A system that runs containers on a pool of machines and keeps them alive. You tell it "I want these things running," and it makes that true and re-makes it true if something crashes.
Container / Image
An image is a frozen, shippable copy of a service (we publish these to GHCR). A container is a running instance of an image.
Pod
K8s's smallest unit — usually one container. When we say "the horus-service pod" we mean the running horus-service.
Deployment
"Keep N copies of this stateless service running." Easy to scale up/down and roll back. Used for services that hold no data of their own.
StatefulSet
Like a Deployment, but for services that own data on disk (databases). Gets stable storage that survives restarts.
PVC (Persistent Volume Claim)
A request for a disk. "Give me 20 GB that survives if the pod restarts." Databases use these.
Service (ClusterIP)
A stable internal address so pods can find each other. ClusterIP = reachable only inside the cluster, not from the internet.
Ingress
The front door from the internet into the cluster. Maps a public URL to an internal Service.
ConfigMap
A bundle of non-secret settings (e.g., "vault-router lives at this internal address").
Secret
Like a ConfigMap but for sensitive values (passwords, keys, tokens).
NetworkPolicy
A firewall rule between pods. We use it to ensure only the front door can reach the internal services.

3What is Kustomize? ← chosen

To run a service in K8s you must hand it YAML files describing the Deployment, Service, ConfigMap, etc. Writing those by hand for 8 services — each slightly different per environment — is repetitive and error-prone. Kustomize solves this without a templating language.

Kustomize is "a default + a stack of patches." You write the canonical YAML once (the base), then a overlay applies small patches for your environment (image tag, domain, replica counts). No {{ placeholders }} — you override real YAML fields by patching them.

Compare: Helm (the alternative we did not pick) fills in template placeholders from a values file. Kustomize instead lays patches on top of plain YAML — easier to read when you're new, and supported by ArgoCD out of the box.

Day-to-day you'd edit the small patch files in overlays/prod/ — the knobs — and leave base/ alone.

4What is ArgoCD? (and "GitOps")

GitOps = your git repo is the single source of truth for what should be running. ArgoCD is a robot living in the cluster that constantly compares "what git says should run" against "what is actually running," and fixes any difference.

Analogy. ArgoCD is a thermostat. Git is the temperature you set. ArgoCD keeps nudging the cluster until reality matches the setting — and if something drifts (a pod dies, someone hand-edits), it pulls it back.

"App-of-apps" (the structure we locked)

One root ArgoCD Application points at your deploy repo. Inside, there's one child Application per service — each rendering its base/<service> through the overlays/prod patches. The root brings up the children; each child watches its own slice, so you can sync/roll back one service at a time.

# your deploy repo — ArgoCD watches this (Kustomize) horus-deploy/ ├── bootstrap/ │ └── argocd-root-app.yaml # the one thing you kubectl apply ├── apps/ # one ArgoCD child app per service │ ├── horus-service.yaml operator-service.yaml │ ├── vault-router.yaml vault-reader.yaml vault-writer.yaml │ └── forge-registry.yaml typesense.yaml neo4j.yaml ├── base/ # canonical YAML per service (don't touch) │ ├── horus-service/ { deployment.yaml, service.yaml, kustomization.yaml } │ ├── operator-service/ vault-router/ vault-reader/ vault-writer/ │ ├── forge-registry/ typesense/ neo4j/ │ └── kustomization.yaml ├── overlays/ │ └── prod/ # the knobs you actually edit │ ├── kustomization.yaml # which bases + which patches │ ├── patches/ { replicas.yaml, resources.yaml, domain.yaml } │ ├── ingress.yaml │ └── service-discovery.yaml # ConfigMap: name → internal address └── README.md # the bootstrap runbook
🔐
Secrets are the one exception. Passwords/keys are not committed to this repo in alpha. horus operator init applies them straight to the cluster (out-of-band). ArgoCD manages everything except secrets, and just references them by name. (Later you can switch to encrypted-secrets-in-git — a clean upgrade.)

5Going from nothing → running, step by step

  1. Prerequisites. You have a K8s cluster with ArgoCD installed. (We document a minimum; k3s on one VM is fine to start.)
  2. Run horus operator init. It asks for: namespace, public domain, image tag, a first-admin username/password, git tokens, Anthropic key, Neo4j password, etc. (auto-generates anything you skip).
  3. It writes the deploy-repo scaffold (the tree above) and applies the Secrets straight to the cluster.
  4. You commit + push the deploy repo to your git host.
  5. You apply the root app — one command: kubectl apply -f bootstrap/argocd-root-app.yaml.
  6. ArgoCD syncs. ConfigMaps + all 8 services come up automatically.
  7. operator-service first boot generates two asymmetric keys (saved as a K8s Secret, never re-created): (1) client-facing verify key — horus-service's TokenVerifier uses this to validate incoming client tokens; (2) internal signing key — horus-service uses this to mint short-lived (60 s) X-Horus-Principal JWTs injected into all internal backend calls. It then seeds your admin user (only if none exists yet).
  8. You log in via horus operator login (over a port-forward) → forced to set a new password.
  9. You provision the first vault: horus operator vault-create <name>. Then end users run horus setup pointed at horus.company.com.

6What we locked

Section D is fully decided. Summary of the choices baked into the diagram and repo layout above.

Orchestration
Kubernetes — any conformant cluster (k3s on a VM for solo; managed K8s for prod). No cloud-specific dependencies.
Packaging
Kustomize (base + prod overlay), not Helm. No templating language.
GitOps
ArgoCD app-of-apps — root app + one child app per service. Per-service sync & rollback.
Services
8 total: horus-service (public ingress — Edge/Identity + Aggregation), operator-service (admin ClusterIP only — user mgmt + Provisioner, ADR-0004), vault-router/reader/writer, forge-registry, typesense, neo4j (all internal). Server images use pinned version tags; rollback = git revert.
Forge
REMOTE — runs inside the cluster (ClusterIP). Migrated from EC2 into the cluster; keeps its S3 artifact backend, SQLite moves to a PVC. Clients access Forge via horus-service.
Vault + Anvil split
Vault is REMOTE (in the cluster). Anvil is LOCAL (user's machine, git-synced via GitSyncEngine). Federation is CLIENT-SIDE: horus-ui-client merges local Anvil results and remote results from horus-service in the browser.
Operator access
operator-service is ClusterIP + kubectl port-forward; CLI-only admin in alpha (no public admin UI yet).
Secrets
Plain K8s Secrets applied out-of-band by horus operator init; ArgoCD manages everything else.
JWT keys (2)
operator-service generates two asymmetric keys on first boot, stores as a Secret, never re-creates: (1) client-facing verify key for horus-service's TokenVerifier; (2) internal signing key for 60 s X-Horus-Principal JWTs injected into backend calls.
Agent chat SDK
Anthropic SDK (not @cursor/sdk/composer-2). horus-service integrates the Anthropic SDK for agent chat features.
horus-ui naming
Client UI is horus-ui (port 8400, image ghcr.io/arjunkhera/horus/ui); browser SPA is horus-ui-client. Formerly called reader-server / reader.
First admin
Seeded from a bootstrap value (only if no users exist); forced password rotation on first login.
