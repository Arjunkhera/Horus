Horus — Identity & Request Flows

Locked alpha design walkthrough. Reflects all finalized Phase 1 decisions: local-only Anvil, two-service control plane (horus-service + operator-service, ADR-0004), principal normalization via X-Horus-Principal, client-side federation, VaultReader/VaultWriter split, Typesense-as-primary-read-store, and local Forge workspaces. Updated 2026-05-28.

Section 0 — Participant Legend

Every actor that appears in the diagrams below, grouped by the plane it belongs to. Colors match the diagram actor labels used throughout.

Control Plane — hosted services (Kubernetes cluster, one per company)
horus-service
The ONLY public ingress. Handles Edge/Identity (TokenVerifier, principal normalization, X-Horus-Principal minting) and Aggregation (federated reads over Vault + Forge). All end-user requests enter here.
operator-service
Separate privileged service (ADR-0004). User management, tenant registry, idempotent Provisioner (create vault, attach forge). ClusterIP + kubectl port-forward only — NO public ingress. CLI-only admin in alpha.
HorusControlPlane (CLI)
The @arkhera/horus NPM CLI. Orchestrates bootstrap, onboarding, and vault lifecycle commands. Runs on the operator's machine.
TokenVerifier / AuthLib
Pluggable TokenVerifier inside horus-service that validates client tokens and produces a canonical Principal {tenant, user, role}. horus-service then mints a short-lived (60 s) internal JWT signed with the internal signing key and injects it as X-Horus-Principal.
Service Plane — hosted backends
VaultRouter
Multi-vault HTTP proxy. Verifies JWT via AuthLib. Routes to VaultReader or VaultWriter based on request method. No tenant checking — network reachability is the boundary.
VaultReader
Stateless read replica (2-3 instances, autoscaled). Reads ONLY from Typesense and Neo4j. Never touches git or the filesystem.
VaultWriter
Single replica. Owns one in-process queue per vault. Holds git working copies on a PVC. Sole writer of git, Typesense, and Neo4j.
ForgeRegistry
S3-backed artifact store. Binary auth: admin key required to publish; anonymous read allowed in alpha. No per-tenant S3 key namespacing (deferred).
Typesense
Shared Typesense instance (one per deployment). Per-vault collections. Stores full page body. Primary read source for Vault.
Neo4j
Shared Neo4j instance (one per deployment). Per-vault databases. Used for graph/relational queries only.
Execution Plane — runs on the user's own machine (4 local containers managed by the horus CLI)
Client
A user's Claude agent, Horus CLI process, or any caller that initiates requests. Runs locally.
horus-ui (port 8400)
Unified client UI. Image ghcr.io/arjunkhera/horus/ui. Web UI + proxy. Routes /api/anvil/* local-direct (no auth header); routes /api/v1/vault/*, /api/v1/forge/*, /api/v1/events (SSE) through horus-service with auth header. Formerly called reader-server.
horus-ui-client
The browser-side SPA bundled with horus-ui. Formerly called reader. Performs client-side federation: queries local Anvil AND the remote control plane in parallel and merges results.
LocalAnvil
The Anvil MCP server running in a local Docker container on the user's machine. Accessible via localhost MCP socket only. Git-synced via the GitSyncEngine.
LocalTypesense
Typesense instance inside the user's local Docker stack. Used exclusively by LocalAnvil.
LocalNeo4j
Neo4j instance inside the user's local Docker stack. Used exclusively by LocalAnvil.
LocalGit
Git working copy on the user's machine. LocalAnvil reads and writes here. Synced to RemoteGit for multi-device via the GitSyncEngine.
External — outside the deployment boundary
S3
Object storage for Forge artifacts. Accessed exclusively by ForgeRegistry. Clients never call S3 directly.
RemoteGit
User's private git remote (e.g. private GitHub repo). Anvil pushes and pulls here for cross-device sync. Not a Horus-managed service.
Human actors
Operator
Human operator running horus CLI admin commands. Manages infrastructure lifecycle and vault creation.
User
End user who was onboarded by the operator and runs Horus on their local machine.

Section 1 — Bootstrapping a Company Deployment

Before any user can authenticate or any vault can be created, an operator must stand up the Horus control plane in a Kubernetes cluster. The cluster runs two control-plane services: horus-service (the only public ingress — handles all end-user requests and principal normalization) and operator-service (a separate privileged service behind ClusterIP only — handles user management, tenant registry, and provisioning). This split is mandated by ADR-0004. operator-service generates the JWT keypairs on first boot. Internal backends (vault-router, vault-reader, vault-writer, forge-registry, typesense, neo4j) are ClusterIP + NetworkPolicy and are reachable only via horus-service. Deployment is managed by Kubernetes + ArgoCD (app-of-apps) + Kustomize. Server images use pinned version tags; rollback = git revert.

  • Neo4j — running but empty. No per-vault databases yet.
  • VaultWriter PVC — empty. No git working copies cloned yet.

Section 2 — Onboarding a User

Onboarding has two parts. First, the operator creates a user account in operator-service (via a port-forwarded CLI call), which issues a credential for the user and delivers it out of band. Second, the user runs horus setup on their local machine, which starts the 4-container local stack (horus-ui, anvil, typesense, neo4j) managed by the @arkhera/horus NPM CLI, and connects Anvil to the user's private git remote for cross-device sync via the GitSyncEngine. The PrincipalStore does not exist in the locked alpha design — every holder of a valid credential has full read and write access to the deployment.

  3. Part B, Step 1 — User runs setup. Alice runs horus setup on her machine (via the @arkhera/horus NPM CLI), providing the credential and the deployment URL. The CLI validates the credential and writes a local config file.
  4. Part B, Step 2 — Start 4-container local stack. The CLI starts 4 Docker containers: horus-ui (port 8400), Anvil MCP server, local Typesense, and local Neo4j. All are managed by the CLI.

  6. Part B, Step 4 — Connect to git remote. The GitSyncEngine adds the user's private git remote (e.g. a private GitHub repo) as the origin for the Anvil sync repo. This remote is used for cross-device sync via push and pull.

Section 3 — Creating a Vault (Operator Only)

Vault creation and deletion are operator-only actions performed via operator-service (accessed through a kubectl port-forward). Users cannot create or delete vaults; they can only read and write within vaults that already exist. Each vault has its own git remote (declared in the deployment config), its own Typesense collection, and its own Neo4j database. VaultWriter does the initialization work; VaultReader becomes aware of the new vault once VaultRouter reloads its config.

sequenceDiagram participant Op as Operator participant HCP as HorusCLI participant OpSvc as operator-service participant VR as VaultRouter participant VW as VaultWriter participant TS as Typesense participant NJ as Neo4j participant RG as RemoteGit Op->>HCP: horus operator vault-create engineering over kubectl port-forward HCP->>OpSvc: POST /vaults with name=engineering and git remote URL OpSvc->>OpSvc: idempotent Provisioner registers vault in tenant registry OpSvc->>RG: initialize empty git repo at declared remote URL for engineering vault RG-->>OpSvc: remote repo ready OpSvc->>VW: provision vault - notify with new vault entry and git remote VW->>RG: git clone working copy of engineering vault into PVC RG-->>VW: working copy cloned VW->>TS: create per-vault Typesense collection horus_engineering TS-->>VW: collection created VW->>NJ: create per-vault Neo4j database engineering NJ-->>VW: database created VW-->>OpSvc: vault worker initialized and queue running OpSvc->>VR: notify config reload - engineering vault now known VR-->>OpSvc: VaultRouter updated known-vault list OpSvc-->>HCP: vault engineering ready HCP-->>Op: Vault engineering is ready. Users can read and write immediately.
  1. Step 1 — Operator command. The operator runs horus operator vault-create engineering via the CLI (which port-forwards to operator-service). The vault name must match a git remote URL already declared in the deployment config.
  2. Step 2 — Idempotent Provisioner registers the vault. operator-service's idempotent Provisioner records the vault in the tenant registry. Repeated calls with the same name are safe.
  3. Step 3 — Initialize remote git repo. operator-service initializes an empty git repository at the declared remote URL. This is the authoritative git store for this vault's markdown files.
  4. Step 4 — VaultWriter clones working copy. operator-service signals VaultWriter to provision the vault. VaultWriter clones a working copy of the vault's git repo into its PVC. This is the working copy VaultWriter's queue workers will use to write files.
  5. Step 5 — Create Typesense collection. VaultWriter creates a per-vault Typesense collection (e.g. horus_engineering) with the standard page schema. All future reads will come from this collection — no separate file-fetch step.
  6. Step 6 — Create Neo4j database. VaultWriter creates a per-vault Neo4j database (e.g. engineering). Graph edges between pages will be stored here.
  7. Step 7 — Start vault worker. VaultWriter starts a per-vault in-process queue worker. This worker is the sole entity that commits to git and updates Typesense and Neo4j for this vault.
  8. Step 8 — VaultRouter config reload. operator-service notifies VaultRouter to reload its known-vault list so that incoming requests for the engineering vault are now routable.
  9. Step 9 — Vault ready. The vault is immediately available for reads and writes by any user holding a valid credential.
Note: After config reload, VaultReader replicas automatically learn the new vault because they route through VaultRouter. No per-replica restart is needed.

Section 4 — User Accessing Their Anvil Data (Entirely Local)

Anvil is entirely local in the locked alpha design. There is no AnvilRouter, no remote Anvil server, and no PrincipalStore involved. The Client (a Claude agent or CLI process) connects to LocalAnvil via a local MCP socket on localhost. All data operations hit LocalTypesense, LocalNeo4j, and LocalGit — all running in Docker containers on the same machine. No network call leaves the user's machine during normal Anvil use.

  1. Step 1 — Client connects via local socket. The Client (Claude Code agent, CLI process) connects to LocalAnvil via a localhost MCP socket. There is no JWT check — the local socket is accessible only from the same machine, so network reachability is the auth gate.
  2. Step 2 — Search or list path. For read operations like anvil_search or anvil_list_by_scope, LocalAnvil queries LocalTypesense. Typesense stores full document bodies, so a single query returns complete results — no secondary fetch from disk.
  3. Step 3 — Create or update path. For write operations like anvil_create_note or anvil_update_note, LocalAnvil upserts the document into LocalTypesense, updates graph edges in LocalNeo4j if applicable, and commits the change to LocalGit with the user slug as the git author. All three writes happen in the same local transaction sequence.
  4. Step 4 — Graph query path. For operations like anvil_get_related or anvil_get_edges, LocalAnvil queries LocalNeo4j for the edge data, then fetches the referenced documents by ID from LocalTypesense to populate the response bodies.
  5. Step 5 — Response. LocalAnvil returns the MCP response to the Client. All of this happens without any network call leaving the user's machine.

Multi-device sync via git

When a user switches to a second machine (or wants to resume after a gap), they run horus setup or a sync command. LocalAnvil pulls the latest commits from RemoteGit and replays any new documents into LocalTypesense and LocalNeo4j to bring the local stores up to date.

  1. Step 1 — Trigger sync. The user runs a sync command or Horus triggers sync at session start. This is a manual or semi-automatic operation in alpha — there is no continuous background sync.
  2. Step 2 — Git fetch and merge. LocalAnvil instructs LocalGit to fetch from RemoteGit and merge the new commits into the local working directory. Fast-forward merges are the expected case; conflict resolution is not automated in Phase 1.
  3. Step 3 — Replay into local stores. LocalAnvil reads the list of files changed since the last-known HEAD and upserts each changed document into LocalTypesense, then updates the corresponding Neo4j graph edges.
  4. Step 4 — Ready. The local Anvil stores are now consistent with the latest committed state. The MCP socket continues serving requests.

Section 5 — User Reading from Vault

The Vault read path is the highest-volume path in the system. The request enters through horus-service, which is the ONLY public ingress. horus-service verifies the client token via its pluggable TokenVerifier, normalizes the identity into a canonical Principal {tenant, user, role}, mints a short-lived (60 s) internal JWT signed with the internal signing key, and injects it as X-Horus-Principal into the downstream call. This is "principal normalization" — any client token format becomes one canonical internal token. Internal backends (vault-router, vault-reader) only need to verify the X-Horus-Principal signature; they never see the raw client token. VaultReader replicas are stateless — any replica can serve any read request.

horus-ui routes /api/anvil/* local-direct with no auth header. HS->>TV: verifyToken with client token alt Token invalid or expired TV-->>HS: error HS-->>HUI: 401 Unauthorized else Token valid TV-->>HS: Principal with tenant plus user plus role HS->>HS: mint 60s internal JWT signed with internal signing key HS->>HS: set X-Horus-Principal header with internal JWT HS->>VR: GET /knowledge/search with X-Horus-Principal replacing raw Authorization VR->>VR: verify X-Horus-Principal signature and locate vault engineering alt Vault not found VR-->>HS: 404 vault not found HS-->>HUI: 404 vault not found else Vault found VR->>VRd: forward GET /knowledge/search to any VaultReader replica VRd->>TS: Typesense search query against horus_engineering collection TS-->>VRd: matching documents with full page body and metadata VRd-->>VR: search results VR-->>HS: search results HS-->>HUI: 200 with page results end end
  1. Step 1 — horus-ui routes the request. horus-ui (running on the user's machine at port 8400) routes /api/v1/vault/* to horus-service and adds the Authorization header with the client token. (By contrast, /api/anvil/* goes local-direct to LocalAnvil with no auth header.)
  2. Step 2 — horus-service verifies the token. horus-service calls its pluggable TokenVerifier with the client token. The TokenVerifier validates the token (signature, expiry, claims) against the client-facing verify key. Invalid tokens return 401 immediately — no downstream call is made.
  3. Step 3 — Principal normalization. TokenVerifier returns a canonical Principal {tenant, user, role}. Any supported client token format (current: JWT; extensible to other formats) is normalized to this single internal shape.
  4. Step 4 — Mint X-Horus-Principal. horus-service mints a short-lived (60 s) internal JWT containing the Principal, signed with the internal signing key (separate from the client-facing verify key). This is injected as the X-Horus-Principal header, replacing the raw Authorization header in all downstream calls.
  5. Step 5 — VaultRouter verifies X-Horus-Principal. VaultRouter verifies the X-Horus-Principal signature using the internal signing key's public counterpart. It never sees the raw client token.
  6. Step 6 — Vault routing. VaultRouter checks that the requested vault name appears in its known-vault list. If not found, it returns 404.
  7. Step 7 — Forward to VaultReader. VaultRouter forwards the request to any available VaultReader replica (round-robin or least-connections). VaultReader is stateless, so any replica can serve any request.
  8. Step 8 — Typesense query. VaultReader queries the per-vault Typesense collection. Because Typesense stores the full page body, a single query returns everything the client needs. No secondary filesystem read is needed.
  9. Step 9 — Return results. Results flow back through VaultRouter → horus-service → horus-ui.
Typesense holds the full page body. There is no separate file-fetch step on the read path. The git working copy on VaultWriter's PVC is the authoritative source, but clients never read from it directly — Typesense is the read cache and it is always up to date because VaultWriter updates it synchronously on every write.
Client-side federation: horus-ui-client (the browser SPA) queries local Anvil AND the remote control plane (horus-service) in parallel and merges results in the browser. horus-service's Aggregation module only federates the REMOTE domains (Vault + Forge). There is no server-side federation of Anvil data.

Graph query path (related pages and edges)

When the client issues a graph query such as fetching related pages or traversing edges, VaultReader queries Neo4j instead of Typesense for the structural data, then optionally fetches document bodies from Typesense for the referenced pages. The same principal normalization flow applies.

sequenceDiagram participant HUI as horus-ui participant HS as horus-service participant VR as VaultRouter participant VRd as VaultReader participant NJ as Neo4j participant TS as Typesense HUI->>HS: GET /api/v1/vault/engineering/knowledge/related with page ID and Authorization header HS->>HS: verify token, normalize Principal, mint X-Horus-Principal HS->>VR: GET /knowledge/related with X-Horus-Principal VR->>VR: verify X-Horus-Principal, locate vault VR->>VRd: forward graph query to VaultReader replica VRd->>NJ: Cypher query against engineering database for related page IDs NJ-->>VRd: list of related page IDs with edge types VRd->>TS: fetch documents by ID list from horus_engineering collection TS-->>VRd: page bodies for related pages VRd-->>VR: related pages with edge metadata VR-->>HS: related pages HS-->>HUI: 200 with related pages
  1. Steps 1-4 — Auth, normalization, and X-Horus-Principal injection. Identical to the standard read path: client token verified by TokenVerifier, Principal normalized, 60 s internal JWT minted and injected as X-Horus-Principal.
  2. Step 5 — Neo4j query. VaultReader issues a Cypher query against the per-vault Neo4j database to retrieve the IDs and edge types of pages related to the requested page.
  3. Step 6 — Typesense fetch by ID. VaultReader fetches the full document bodies for the related page IDs from Typesense. This is a batch fetch-by-ID operation, not a search query.
  4. Step 7 — Return. VaultReader combines the Neo4j edge metadata with the Typesense document bodies and returns the enriched result up through VaultRouter and horus-service to horus-ui.

Section 6 — User Writing to Vault

All writes to a vault go through horus-service (which does principal normalization and injects X-Horus-Principal), then through VaultRouter, then to VaultWriter — the single replica that owns the per-vault in-process queue, the git working copies, and all mutations to Typesense and Neo4j. The queue serializes writes per vault to prevent concurrent git conflicts. VaultWriter performs an optimistic version check before writing; if the client is working from a stale version, it receives a 409 and must retry with the latest version.

sequenceDiagram participant HUI as horus-ui participant HS as horus-service participant TV as TokenVerifier participant VR as VaultRouter participant VW as VaultWriter participant TS as Typesense participant NJ as Neo4j participant PVC as PVC git working copies participant RG as RemoteGit HUI->>HS: POST /api/v1/vault/engineering/knowledge/pages with Authorization Bearer token and page body and expected version HS->>TV: verifyToken with client token alt Token invalid TV-->>HS: error HS-->>HUI: 401 Unauthorized else Token valid TV-->>HS: Principal with tenant plus user plus role HS->>HS: mint 60s internal JWT and set X-Horus-Principal HS->>VR: POST /knowledge/pages with X-Horus-Principal plus page body plus expected version VR->>VR: verify X-Horus-Principal signature and locate vault engineering VR->>VW: forward POST to VaultWriter - only one replica exists VW->>VW: enqueue task on the engineering vault queue Note over VW: Queue ensures one writer at a time per vault.
Tasks processed in FIFO order. VW->>VW: vault worker picks up task VW->>VW: optimistic version check - sha256 of current file vs expected version in request alt Version mismatch - stale client VW-->>VR: 409 Conflict with current version VR-->>HS: 409 Conflict HS-->>HUI: 409 Conflict - retry with latest version else Version matches or new page VW->>PVC: write file to git working copy PVC-->>VW: file written VW->>TS: upsert document with full body into horus_engineering collection TS-->>VW: ok VW->>NJ: update graph edges for this page in engineering database NJ-->>VW: ok VW->>PVC: git commit with Principal.user from X-Horus-Principal as author PVC-->>VW: committed VW->>RG: git push to vault remote RG-->>VW: pushed VW-->>VR: 200 with new version sha256 VR-->>HS: 200 with new version HS-->>HUI: 200 with updated page and new version end end
  1. Step 1 — horus-ui routes the write request. horus-ui routes /api/v1/vault/* POSTs to horus-service with the Authorization header. The page body and expected version (sha256 of the content the client last read) are included.
  2. Step 2 — Token verification and principal normalization. horus-service calls its TokenVerifier. Invalid tokens return 401 immediately. Valid tokens produce a canonical Principal {tenant, user, role}.
  3. Step 3 — Mint X-Horus-Principal. horus-service mints a 60 s internal JWT from the Principal and injects it as X-Horus-Principal. The raw Authorization header is NOT forwarded downstream.
  4. Step 4 — VaultRouter receives with X-Horus-Principal. VaultRouter verifies the X-Horus-Principal signature, routes to vault engineering, and forwards to VaultWriter (exactly one replica — no load balancing for writes).
  5. Step 5 — Enqueue task. VaultWriter enqueues the write task on the per-vault in-process queue for the engineering vault. The queue ensures that only one write executes at a time for this vault, preventing concurrent git conflicts.
  6. Step 6 — Vault worker picks up task. The per-vault queue worker dequeues the task and begins processing.
  7. Step 7 — Optimistic version check. The worker computes the sha256 of the current file content on disk and compares it to the expected version in the request. If they do not match, the client is working from a stale version.
  8. Step 8 — Version conflict path. If the version check fails, the worker returns 409 Conflict with the current version. The client must re-read the page, merge its changes, and retry the write.
  9. Step 9 — Write to git working copy. If the version check passes (or this is a new page), the worker writes the file to the git working copy on the PVC.
  10. Step 10 — Update Typesense. The worker upserts the full page body and metadata into the per-vault Typesense collection. After this point, read replicas will return the new content.
  11. Step 11 — Update Neo4j. If the page has link or edge changes, the worker updates the per-vault Neo4j database.
  12. Step 12 — Git commit and push. The worker commits the change with Principal.user (from the X-Horus-Principal JWT) as the git commit author and pushes to the vault's remote git repo. This provides a durable, auditable history.
  13. Step 13 — Respond. VaultWriter returns 200 with the new version (sha256 of the written content). The response flows back through VaultRouter and horus-service to horus-ui.
No caching layer exists in Phase 1. No batch write API exists in Phase 1. Each write goes through the queue individually.

Section 7 — User Installing Workspace Artifacts via Forge

Forge is a REMOTE service in the locked architecture. The Forge Registry runs inside the Kubernetes cluster (ClusterIP, reachable only via horus-service) — it is not a local service on the user's machine. Workspaces are still a local execution-plane concept: directories on the user's machine created by the @arkhera/horus NPM CLI with no remote service calls. But artifact resolution and download go through horus-service (which applies principal normalization and injects X-Horus-Principal) before reaching forge-registry. Sessions (forge_develop) are local git worktrees, separate from workspaces.

It writes config files including mcp.json, a skills list, and permissions. This is a pure filesystem operation — no network call is made to any Horus service. Workspaces do NOT clone repositories.
  2. Step 2 — Artifact resolution via horus-service. When the user adds an artifact, horus-ui sends the request to horus-service at /api/v1/forge/resolve. horus-service verifies the token, normalizes the Principal, and mints an X-Horus-Principal JWT before forwarding to forge-registry (which is ClusterIP only — not reachable directly).
  3. Step 3 — forge-registry resolves the artifact. forge-registry verifies the X-Horus-Principal and returns artifact metadata with the resolved version and a download URL.
  4. Step 4 — Download via horus-service. horus-ui sends the download request through horus-service, which again applies principal normalization. forge-registry fetches the tarball from S3 using an internal storage key. Clients never interact with S3 directly.
  5. Step 5 — Install locally. horus-ui extracts the tarball and installs the artifact into the workspace directory. The workspace is now ready to use with the artifact available.

  1. Step 1 — Publish request. The publisher (operator or CI system) sends the artifact tarball and metadata to horus-service's publish endpoint with an admin credential in the Authorization header. forge-registry is ClusterIP only — not reachable directly.
  2. Step 2 — Token verification and role check. horus-service's TokenVerifier verifies the credential and produces a Principal with role=admin. If absent or invalid, the request is rejected with 403.
  3. Step 3 — Principal normalization. horus-service mints an X-Horus-Principal JWT with the admin role and forwards to forge-registry. forge-registry verifies the JWT and checks the role.
  4. Step 4 — S3 write. forge-registry writes the tarball to S3 under a storage key structured as artifacts/name/version.tar.gz. Note: keys are not namespaced by tenant in Phase 1 — all tenants share the same S3 key namespace.
  5. Step 5 — Index update. forge-registry updates its registry index (SQLite on a PVC) with the artifact name, version, sha256 checksum, and manifest. Future resolve calls will find this version.
  6. Step 6 — Confirmation. A 201 response with the artifact download URL flows back through horus-service to the publisher.
Tenant gap (post-alpha): S3 storage keys are not namespaced by tenant. All users sharing a forge-registry deployment share the same artifact namespace. True isolation requires either key-prefix scoping per tenant or separate S3 buckets per tenant. This is a known deferred item for post-alpha.

Section 9 — Open Questions for Later

Locked since last revision: Agent chat uses the Anthropic SDK (not @cursor/sdk/composer-2). horus-service integrates the Anthropic SDK for agent chat features. horus-ui is the unified client UI (port 8400), formerly called reader-server. The client-side SPA is horus-ui-client, formerly called reader. Forge is REMOTE (behind horus-service); Vault is REMOTE. Only Anvil is LOCAL. Federation is CLIENT-SIDE: horus-ui-client merges local Anvil results and remote (horus-service) results in the browser.

  1. Local Anvil setup ergonomics. horus setup needs to start a Docker or Podman stack on the user's machine automatically. Questions include: how does the CLI detect whether Docker or Podman is available; how are port conflicts handled; how does the user know which MCP socket address to configure in Claude Code; and how is the Anvil stack updated when new default types ship. A guided setup wizard or a CLI doctor command would help surface these issues.
  2. Multi-device Anvil git sync UX. In the locked alpha, sync is manual — the user runs a sync command or it triggers at session start. There is no conflict resolution automation if two devices write to the same note concurrently. Questions to answer: should sync be automatic in the background; how should merge conflicts surface to the user; and should the system use git-level conflict markers or a higher-level CRDT approach for Anvil note content.
  3. Vault create and delete CLI surface. The current design positions vault creation as an operator-only out-of-band action, but the CLI surface for horus vault create and horus vault delete is not fully specified. Questions include: what happens to data in Typesense and Neo4j when a vault is deleted; how is the git remote archived or removed; and what is the rollback procedure if vault creation partially fails partway through the initialization sequence.
  4. S3 binary attachment support for Vault (next phase). The locked alpha stores only markdown-in-git. Binary file support (images, PDFs, attachments) requires S3 or equivalent object storage. Questions for the next phase: how are S3 references embedded in markdown; how does VaultReader serve binary blobs (presigned URLs vs. proxy); and whether the binary store is per-vault or shared with Forge Registry storage.
  5. Forge Registry tenant scoping (post-alpha). S3 keys are currently not namespaced by tenant, meaning all users sharing a ForgeRegistry instance share the artifact namespace. Questions for post-alpha: does Horus become a shared-registry SaaS (requiring key-prefix scoping or separate S3 buckets per tenant), or does each company deployment receive its own ForgeRegistry instance (natural isolation through separate buckets); and how does artifact versioning interact with tenant scoping if the same artifact name exists for multiple tenants.
