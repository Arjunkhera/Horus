Horus — Identity & Request Flows

A traced walkthrough of every identity decision in the system, from bootstrap through live request routing. Reflects Phase 1 shipped code plus the proposed Track A / PrincipalStore design.

Section 0 — Participant Legend

Every actor that appears in the diagrams below, grouped by the plane it belongs to. Colors are used consistently across all diagrams.

Execution Plane — runs on the user's machine
Client
A user's agent, Horus CLI, or browser session that initiates requests.
Operator
Human operator running horus CLI admin commands; manages infra lifecycle.
Control Plane — identity, tenancy, governance
HorusControlPlane
The orchestrating CLI sub-system that drives bootstrap and onboarding commands.
AuthLib
@horus/auth — JWT sign/verify library. Stateless; called inline by every router.
PrincipalStore
Proposed new layer. Reads principals.yaml + resources.yaml (file-watched) or a SQLite table. Used only for shared-resource authorization, not per-user routing.
ServiceRegistry
SQLite table keyed (tenant, user) → backend URL. Consulted by routers to find the physical service endpoint for a given principal.
Service Plane — hosted backends and routers
AnvilRouter
HTTP router sitting in front of all per-user Anvil backends. Verifies JWT, looks up backend, proxies request.
AnvilBackend
Per-user Anvil MCP server instance (Typesense collection + Neo4j database). Only the router can address it directly.
VaultRouter
Multi-vault proxy. Resolves the requested vault slug(s) to physical backend URLs, fan-outs on ** wildcard queries.
VaultBackend
Individual Vault REST service (Python/FastAPI). Owns one Markdown repository + one Typesense collection.
ForgeRegistry
Forge artifact registry (S3-backed). Binary auth strategy: admin or anonymous. No per-tenant storage keys yet.
S3
Object storage for Forge artifacts. Accessed exclusively through ForgeRegistry; clients never call S3 directly.

Section 1 — Bootstrapping an Enterprise Deployment

Before any user can authenticate, an operator must stand up the Horus control plane and declare the initial topology. This section covers everything that must exist on disk and in the database before the first horus user add can succeed. Critically, the Control Plane does not auto-discover service URLs — the operator declares them explicitly in a config file that is loaded during bootstrap.

AnvilRouter, VaultRouter, ForgeRegistry.
Control Plane does NOT auto-discover. HCP->>SR: initServiceRegistry() SR-->>HCP: SQLite DB created (empty rows) HCP->>HCP: start services (docker compose up) HCP->>AnvilRouter: GET /health AnvilRouter-->>HCP: 200 OK HCP->>VaultRouter: GET /health VaultRouter-->>HCP: 200 OK HCP->>ForgeRegistry: GET /health ForgeRegistry-->>HCP: 200 OK HCP-->>Op: Bootstrap complete. Keypair at data/keys/acme/. JWT public key distributed to services.
  1. Step 1 — Operator invokes bootstrap. The human operator runs horus bootstrap --tenant acme. The HorusControlPlane is the orchestrating CLI subsystem that handles the command.
  2. Step 2 — Keypair generation. HorusControlPlane calls AuthLib.generateKeypair(). AuthLib returns an asymmetric keypair (e.g. RS256 or EdDSA). The private key is used to sign JWTs; the public key is distributed to all service routers so they can verify tokens without calling back to the control plane.
  3. Step 3 — Persist keypair. The keypair is written to data/keys/acme/ on the operator's host filesystem. The exact location is operator-configured; see Open Questions for rotation concerns.
  4. Step 4 — Initialize PrincipalStore files. principals.yaml is created with a single entry for the operator. resources.yaml starts empty (no shared vaults registered yet). These are the on-disk source-of-truth for the PrincipalStore.
  5. Step 5 — Load service topology. The Control Plane reads a declarative topology.yaml (operator-authored) that maps logical service names to physical URLs. This is a deliberate design choice: there is no service discovery protocol — URLs are declared, not auto-discovered. This prevents misconfigured services from silently routing to wrong backends.
  6. Step 6 — Initialize ServiceRegistry. The SQLite database file is created with an empty service_registry table. No user rows exist yet; they are inserted during onboarding.
  7. Step 7 — Start services. Docker Compose brings up AnvilRouter, VaultRouter, ForgeRegistry, and their dependent services (Typesense, Neo4j). Each service receives the JWT public key as an environment variable or mounted file.
  8. Step 8 — Health checks. The Control Plane polls each service's /health endpoint and fails the bootstrap if any service is unresponsive.
  9. Step 9 — Bootstrap complete. The operator is informed of the keypair location. At this point the system is live but has no end-users; all backend routing tables are empty.

What is persisted by the end of bootstrap

  • JWT keypair — private key + public key at data/keys/<tenant>/.
  • principals.yaml — one entry for the operator principal, no users yet.
  • resources.yaml — empty; no shared vaults or other shared resources declared.
  • topology.yaml — operator-authored; read-only at runtime. Contains physical URLs for all routers and registries.
  • ServiceRegistry SQLite DB — schema initialized, zero data rows.
  • Running service processes — AnvilRouter, VaultRouter, ForgeRegistry, Typesense, Neo4j, all healthy.

Section 2 — Onboarding a User (Enterprise Mode)

In enterprise mode, users are provisioned by an operator, not by self-signup (SaaS signup is deferred post-alpha). Onboarding is a multi-step pipeline: validate the slug, provision the Anvil backend, register the backend URL, then issue and deliver a JWT. Each step is idempotent — re-running horus user add for an existing user should be safe.

sequenceDiagram participant Op as Operator participant HCP as HorusControlPlane participant PS as PrincipalStore participant SR as ServiceRegistry participant AnvilBackend as AnvilBackend participant AuthLib as AuthLib Op->>HCP: horus user add --tenant acme --user alice HCP->>HCP: validate slug is DNS-safe (alphanum + hyphens only) HCP->>PS: addPrincipal(tenant=acme, user=alice, role=user) PS-->>HCP: principals.yaml updated HCP->>AnvilBackend: provisionUser(tenant=acme, user=alice) Note over AnvilBackend: Create Typesense collection acme_alice
Create Neo4j database acme_alice
Apply base schema (default types) AnvilBackend-->>HCP: backend URL returned (e.g. http://anvil-alice:3001) HCP->>SR: registerBackend(tenant=acme, user=alice, url=http://anvil-alice:3001) SR-->>HCP: row inserted HCP->>AuthLib: issueJWT(sub=alice, tenant=acme, ttl=long) AuthLib-->>HCP: signed JWT token HCP-->>Op: User provisioned. JWT (deliver out-of-band to alice).
  1. Step 1 — Operator command. The operator runs horus user add --tenant acme --user alice. The username alice will appear as part of routing keys and resource identifiers.
  2. Step 2 — Slug validation. The Control Plane validates that the username is DNS-safe: lowercase alphanumeric characters and hyphens only, no underscores or dots. This is enforced because the slug is used to construct Typesense collection names, Neo4j database names, and possibly subdomain routing in future.
  3. Step 3 — PrincipalStore write. A new entry is appended to principals.yaml with tenant: acme, user: alice, and role: user. The file-watcher in PrincipalStore picks up the change without a restart. This record gates shared-resource access (Vault); it is NOT used for Anvil routing.
  4. Step 4 — Provision Anvil backend. The Control Plane calls the Anvil provisioning API, which creates a dedicated Typesense collection named acme_alice and a Neo4j database named acme_alice. The base schema (built-in default types from packages/anvil/defaults/) is applied. Provisioning returns the physical URL of this backend.
  5. Step 5 — ServiceRegistry registration. The returned backend URL is written to the ServiceRegistry as a new row: (tenant=acme, user=alice) → http://anvil-alice:3001. This is the only thing AnvilRouter needs to route requests for Alice.
  6. Step 6 — JWT issuance. AuthLib signs a JWT with claims sub=alice, tenant=acme, and a long TTL (e.g. 1 year for personal deployments; shorter for enterprise). The private key used is the one generated during bootstrap.
  7. Step 7 — Out-of-band delivery. The operator receives the JWT and delivers it to Alice through a secure channel (email, password manager share, etc.). Horus has no in-band delivery mechanism in Phase 1.

Section 3 — User Accessing Their Anvil Data (Private)

Every user's Anvil backend is private — no other user can access it, and there are no shared Anvil resources in Phase 1. This means the PrincipalStore is not involved in this flow: once the JWT is verified and the routing key is extracted, the only question is "what is Alice's backend URL?" — a pure ServiceRegistry lookup. If the ServiceRegistry has no entry for the user (cold-start or missed onboarding step), the router returns 404 rather than silently proxying to a wrong backend.

sequenceDiagram participant C as Client participant AR as AnvilRouter participant AL as AuthLib participant SR as ServiceRegistry participant AB as AnvilBackend C->>AR: POST /mcp/tools/invoke Authorization: Bearer <jwt> AR->>AL: verifyJWT(token) alt JWT invalid or expired AL-->>AR: error AR-->>C: 401 Unauthorized else JWT valid AL-->>AR: claims (sub=alice, tenant=acme) AR->>SR: lookup(tenant=acme, user=alice) alt No entry found SR-->>AR: null AR-->>C: 404 No backend registered for this principal else Entry found SR-->>AR: http://anvil-alice:3001 AR->>AB: proxy POST /mcp/tools/invoke Authorization: Bearer <jwt> Note over AB: AnvilBackend trusts forwarded JWT.
No second verification needed
(router is the trust boundary). AB-->>AR: MCP response payload AR-->>C: response (transparent proxy) end end
  1. Step 1 — Client sends request. The Client (agent, CLI, or browser) sends an MCP call to the AnvilRouter's address, including the JWT in the Authorization: Bearer header.
  2. Step 2 — JWT verification. AnvilRouter calls AuthLib.verifyJWT(). AuthLib checks the signature against the tenant's public key and confirms the token has not expired. This is a pure in-process call — no network round-trip to the Control Plane.
  3. Step 3 — Invalid JWT path. If verification fails (bad signature, expired, wrong issuer), the router immediately returns 401 Unauthorized and does not consult the ServiceRegistry at all.
  4. Step 4 — Extract routing key. From the verified claims, AnvilRouter extracts (tenant=acme, user=alice). This pair is the ServiceRegistry lookup key.
  5. Step 5 — ServiceRegistry lookup. The router queries the SQLite table for a row matching (acme, alice). If no row exists — because the user was not onboarded or onboarding failed — the router returns 404 (not a 401; authentication succeeded but provisioning did not).
  6. Step 6 — Transparent proxy. The router forwards the original request verbatim to the discovered backend URL, preserving the Authorization header. The AnvilBackend does not re-verify the JWT; it trusts that the router is the ingress trust boundary. This keeps backend code simple.
  7. Step 7 — Response passthrough. The AnvilBackend returns its MCP response. The router passes it back to the client with no modification.
Cold-start note: if AnvilRouter starts before onboarding completes (race condition), lookups return 404. The client should retry with exponential backoff. The router must never fall back to a default backend.

Section 4 — User Accessing Vault Data (Shared)

Vault namespaces like acme/engineering are shared across tenant members — this is where the PrincipalStore matters. After JWT verification, VaultRouter consults PrincipalStore to retrieve the list of vault namespaces the caller may access, then checks whether the requested namespace is in that list before resolving the physical backend URL.

sequenceDiagram participant C as Client participant VR as VaultRouter participant AL as AuthLib participant PS as PrincipalStore participant VB as VaultBackend C->>VR: GET /vault/acme/engineering/knowledge/search Authorization: Bearer <jwt> VR->>AL: verifyJWT(token) alt JWT invalid AL-->>VR: error VR-->>C: 401 Unauthorized else JWT valid AL-->>VR: claims (sub=alice, tenant=acme) VR->>PS: resolvePrincipal(tenant=acme, user=alice) PS-->>VR: allowedVaults list (e.g. acme/engineering, acme/docs) alt Requested vault not in allowedVaults VR-->>C: 403 Forbidden (vault not accessible to this principal) else Vault is accessible VR->>VR: locate backend URL for acme/engineering (from topology.yaml) VR->>VB: proxy GET /knowledge/search Authorization: Bearer <jwt> VB-->>VR: search results VR-->>C: merged response end end
  1. Step 1 — Client request. The client calls the VaultRouter with a path that encodes the vault namespace (acme/engineering) and the operation (/knowledge/search).
  2. Step 2 — JWT verification. Identical to the Anvil flow: AuthLib verifies the token in-process; invalid tokens short-circuit with 401.
  3. Step 3 — PrincipalStore resolve. VaultRouter calls PrincipalStore.resolvePrincipal(tenant, user). The store checks principals.yaml to confirm the principal exists, then reads resources.yaml to build the allowed-vault list for that principal. This is the key step absent from the Anvil flow.
  4. Step 4 — Authorization check. If the requested vault namespace is not in the allowed list, the router returns 403 Forbidden. Authentication succeeded but authorization failed.
  5. Step 5 — Backend URL resolution. VaultRouter looks up the physical URL for acme/engineering from topology.yaml (the same operator-declared topology loaded at bootstrap). The PrincipalStore does not know about URLs — it only knows about which namespaces a principal may access.
  6. Step 6 — Proxy and return. The request is forwarded to the VaultBackend; the response is passed back to the client.

Wildcard fan-out: searching across all accessible vaults (**)

When a client requests the special ** vault path, VaultRouter fans the query out to all vaults in the caller's allowed list, collects results, and merges them before returning. This is how cross-vault search works.

sequenceDiagram participant C as Client participant VR as VaultRouter participant AL as AuthLib participant PS as PrincipalStore participant VB1 as VaultBackend participant VB2 as VaultBackend C->>VR: GET /vault/**/knowledge/search?q=anvil Authorization: Bearer <jwt> VR->>AL: verifyJWT(token) AL-->>VR: claims (sub=alice, tenant=acme) VR->>PS: resolvePrincipal(tenant=acme, user=alice) PS-->>VR: allowedVaults (acme/engineering, acme/docs) par Fan-out to each allowed vault VR->>VB1: GET /knowledge/search?q=anvil (acme/engineering) VB1-->>VR: results (scored) and VR->>VB2: GET /knowledge/search?q=anvil (acme/docs) VB2-->>VR: results (scored) end VR->>VR: merge + re-rank results by score VR-->>C: merged results with vault source labels
  1. Step 1-3 — Auth and PrincipalStore. Identical to the single-vault flow: verify JWT, resolve principal to allowed-vault list.
  2. Step 4 — Fan-out. VaultRouter issues concurrent requests to every backend in the allowed list. Each request carries the original query string and the forwarded Authorization header.
  3. Step 5 — Collect results. VaultRouter waits for all backends to respond (or times out individually). Each backend returns scored results in its own namespace.
  4. Step 6 — Merge and re-rank. Results from all vaults are merged into a single list and re-ranked by relevance score. Each result is labeled with its source vault namespace so the client can show provenance.
  5. Step 7 — Return. The merged, labeled result set is returned to the client as a single response.

Section 5 — User Creating Workspace Artifacts in Forge through Horus

Forge has two distinct layers that are easily confused: the local workspace (a directory at ~/Horus/workspaces/<name>/ on the user's machine, holding config and installed artifacts) and the remote Forge Registry (an S3-backed artifact store running as a hosted service). The CLI mediates between them. Workspaces are an execution-plane concept; the registry is a service-plane concept.

  1. Step 1 — Workspace creation (local only). forge_workspace_create creates a directory on the user's local filesystem at ~/Horus/workspaces/<name>/. It writes config files (mcp.json, skills list, permissions). This is a pure filesystem operation — no network call is made to any Horus service. Workspaces do NOT clone repos.
  2. Step 2 — Artifact resolution. When the user adds an artifact (skill, plugin, tool), the CLI calls the ForgeRegistry's resolve endpoint to find the latest matching version and obtain a download URL.
  3. Step 3 — AuthStrategy check. ForgeRegistry evaluates the request through its AuthStrategy. In Phase 1, reads are anonymous (no JWT required). This is a known gap — see the post-alpha note below.
  4. Step 4 — S3 retrieval. ForgeRegistry fetches the artifact bytes from S3 using the internal storage key. Clients never call S3 directly — ForgeRegistry owns all S3 access.
  5. Step 5 — Install. The CLI writes the downloaded artifact into the workspace directory. The workspace is now ready to use.

Publishing a new artifact

sequenceDiagram participant C as Client participant FR as ForgeRegistry participant S3 as S3 C->>FR: POST publish - tarball plus metadata plus admin key in Authorization FR->>FR: AuthStrategy authorize the request alt Not authorized - missing or wrong admin key FR-->>C: 403 Forbidden else Authorized FR->>S3: putObject artifact tarball at artifacts name version key S3-->>FR: etag confirmed FR->>FR: update registry index - name version sha256 manifest FR-->>C: 201 Created with artifact URL end
  1. Step 1 — Publish request. The publisher (operator or CI) sends the artifact tarball and metadata to ForgeRegistry's publish endpoint, including an admin API key in the Authorization header.
  2. Step 2 — Authorization. ForgeRegistry's AuthStrategy checks the admin key. If absent or invalid, the request is rejected with 403. Anonymous callers cannot publish.
  3. Step 3 — S3 write. The tarball is written to S3 under a key structured as artifacts/<name>/<version>.tar.gz. Note: keys are NOT scoped by tenant — all tenants share the same key namespace in Phase 1.
  4. Step 4 — Index update. ForgeRegistry updates its in-memory and/or SQLite index with the new artifact's name, version, SHA-256 checksum, and manifest. Future resolve calls will find this version.
  5. Step 5 — Confirmation. A 201 response with the artifact URL is returned to the publisher.
Post-alpha note — Forge Registry tenant gap: S3 storage keys are not namespaced by tenant. All tenants share the artifact namespace. A tenant with an admin key can overwrite another tenant's artifact at the same name+version. True multi-tenancy in Forge Registry requires either key-prefix scoping per tenant or a separate registry instance per tenant. This is a known deferred item.

Section 7 — Open Questions

  1. Operator keypair location and rotation. Where exactly should the private key live — on the operator's local filesystem, in a secrets manager, or in a Docker secret? More importantly: what is the rotation procedure? Rotating the private key means all existing JWTs (which are long-lived) become invalid simultaneously, forcing re-issuance for every user. A key-versioning scheme (keep N previous keys valid) is needed before rotation is operationally safe.
  2. Offboarding flow. There is no horus user remove procedure defined. Offboarding needs to: (a) remove the principal from principals.yaml, (b) delete the ServiceRegistry row, (c) optionally archive or destroy the Typesense collection and Neo4j database, and (d) invalidate the user's JWT. Step (d) is impossible without a token revocation list, since JWTs are self-contained and cannot be un-signed.
  3. Forge Registry tenant scoping. As noted in Section 5, all tenants share a flat S3 key namespace. The decision to defer tenant scoping in Forge storage means a multi-tenant Forge deployment has no isolation guarantees. The open question is: does Horus ever become a shared-registry SaaS, or does each enterprise deployment get its own ForgeRegistry instance (which would naturally provide isolation through separate S3 buckets)?
  4. Is principals.yaml git-tracked or runtime-only? If principals.yaml is committed to a git repository, adding a user creates a git commit — which is auditable but requires git credentials at runtime and creates a branch-management concern. If it is runtime-only (on-disk, not git-tracked), it can be edited freely but loses the audit trail and is not automatically backed up. The choice also affects how PrincipalStore's file-watcher interacts with concurrent writes.
  5. Cold-start ordering between onboarding steps. Onboarding has a dependency chain: PrincipalStore write → Anvil provision → ServiceRegistry write → JWT issue. If the Anvil provisioning call fails (e.g. Typesense is temporarily unavailable), the principal is already in principals.yaml but the ServiceRegistry has no row — the user exists as a principal but cannot access Anvil. A saga/compensating-transaction pattern or a two-phase commit approach is needed to ensure all steps succeed or all roll back atomically.
