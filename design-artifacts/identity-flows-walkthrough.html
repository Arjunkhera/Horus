Horus — Identity & Request Flows

Locked alpha design walkthrough. Reflects all finalized Phase 1 decisions: local-only Anvil, single-tenant per deployment, VaultReader/VaultWriter split, Typesense-as-primary-read-store, and local Forge workspaces. Generated 2026-05-25.

Section 0 — Participant Legend

Every actor that appears in the diagrams below, grouped by the plane it belongs to. Colors match the diagram actor labels used throughout.

Control Plane — deployment orchestration
HorusControlPlane
The Horus CLI sub-system that orchestrates bootstrap, onboarding, and vault lifecycle commands. Runs on the operator's machine.
AuthLib
@horus/auth — stateless JWT sign and verify library. Called inline by routers. No network call required.
Service Plane — hosted backends
VaultRouter
Multi-vault HTTP proxy. Verifies JWT via AuthLib. Routes to VaultReader or VaultWriter based on request method. No tenant checking — network reachability is the boundary.
VaultReader
Stateless read replica (2-3 instances, autoscaled). Reads ONLY from Typesense and Neo4j. Never touches git or the filesystem.
VaultWriter
Single replica. Owns one in-process queue per vault. Holds git working copies on a PVC. Sole writer of git, Typesense, and Neo4j.
ForgeRegistry
S3-backed artifact store. Binary auth: admin key required to publish; anonymous read allowed in alpha. No per-tenant S3 key namespacing (deferred).
Typesense
Shared Typesense instance (one per deployment). Per-vault collections. Stores full page body. Primary read source for Vault.
Neo4j
Shared Neo4j instance (one per deployment). Per-vault databases. Used for graph/relational queries only.
Execution Plane — runs on the user's own machine
Client
A user's Claude agent, Horus CLI process, or any caller that initiates requests. Runs locally.
LocalAnvil
The Anvil MCP server running in a local Docker container on the user's machine. Accessible via localhost MCP socket only.
LocalTypesense
Typesense instance inside the user's local Docker stack. Used exclusively by LocalAnvil.
LocalNeo4j
Neo4j instance inside the user's local Docker stack. Used exclusively by LocalAnvil.
LocalGit
Git working copy on the user's machine. LocalAnvil reads and writes here. Synced to RemoteGit for multi-device.
External — outside the deployment boundary
S3
Object storage for Forge artifacts. Accessed exclusively by ForgeRegistry. Clients never call S3 directly.
RemoteGit
User's private git remote (e.g. private GitHub repo). Anvil pushes and pulls here for cross-device sync. Not a Horus-managed service.
Human actors
Operator
Human operator running horus CLI admin commands. Manages infrastructure lifecycle and vault creation.
User
End user who was onboarded by the operator and runs Horus on their local machine.

Section 1 — Bootstrapping a Company Deployment

Before any user can authenticate or any vault can be created, an operator must stand up the Horus service plane. This is a one-time operation per company. The operator provisions infrastructure, generates the JWT keypair, declares the deployment configuration, and starts all services. No multi-tenancy is involved — the deployment itself is the tenancy boundary. Every authenticated user in this deployment has full read and write access.

sequenceDiagram participant Op as Operator participant HCP as HorusControlPlane participant AL as AuthLib participant VR as VaultRouter participant VRd as VaultReader participant VW as VaultWriter participant FR as ForgeRegistry participant TS as Typesense participant NJ as Neo4j Op->>HCP: horus bootstrap HCP->>AL: generateKeypair AL-->>HCP: privateKey plus publicKey HCP->>HCP: persist keypair to deployment config dir HCP->>HCP: load deployment config with tenant name, vault git remotes, S3 creds for Forge Note over HCP: Tenant name is hard-coded in the config.

S3 bucket and credentials for ForgeRegistry declared here.   1. Step 1 — Operator invokes bootstrap. The human operator runs horus bootstrap. The HorusControlPlane CLI sub-system handles the command.
  2. Step 2 — Keypair generation. HorusControlPlane calls AuthLib.generateKeypair(). AuthLib returns an asymmetric keypair (RS256 or EdDSA). The private key signs JWTs; the public key is distributed to service routers for in-process verification with no network round-trip.
  3. Step 3 — Persist keypair. The keypair is written to the deployment config directory. The public key will be injected into each service's environment at start time.
  4. Step 4 — Load deployment config. The operator-authored deployment config declares the tenant name (hard-coded string), the git remote URLs for each vault, and the S3 bucket and credentials for the Forge Registry. The Control Plane reads this at bootstrap and does not auto-discover anything.
  5. Step 5 — Start service plane. VaultRouter, VaultReader (two replicas), VaultWriter (one replica), ForgeRegistry, Typesense, and Neo4j are all started with the public key injected.
  6. Step 6 — Health checks. The Control Plane polls each service's /health endpoint. Bootstrap fails if any service is unresponsive.
  7. Step 7 — Bootstrap complete. The service plane is live. No vaults exist yet (Typesense and Neo4j are empty, VaultWriter PVC is empty). The operator must now issue user JWTs and create vaults before users can do anything.

Persisted by end of bootstrap

  • JWT keypair — stored in deployment config directory. Public key injected into all service environments.
  • Deployment config — tenant name, vault git remote URLs, S3 credentials, service addresses. Operator-authored; read-only at runtime.
  • Typesense — running but empty. No per-vault collections yet.
  • Neo4j — running but empty. No per-vault databases yet.
  • VaultWriter PVC — empty. No git working copies cloned yet.
  • No vaults exist yet. Vault creation is a separate operator action (Section 3).

Section 2 — Onboarding a User

Onboarding has two parts. First, the operator issues a JWT for the user and delivers it out of band. Second, the user runs horus setup on their local machine, which starts the local Anvil stack and connects it to the user's private git remote for cross-device sync. The PrincipalStore does not exist in the locked alpha design — every holder of a valid JWT has full read and write access to the deployment.

Part A — Operator side: issuing the JWT

sequenceDiagram participant Op as Operator participant HCP as HorusControlPlane participant AL as AuthLib Op->>HCP: horus user add --user alice HCP->>HCP: validate slug is DNS-safe lowercase alphanumeric or hyphens HCP->>AL: issueJWT with sub=alice, tenant from config, long TTL AL-->>HCP: signed JWT HCP-->>Op: JWT token - deliver to alice out of band

Part B — User side: local setup

sequenceDiagram participant U as User participant HCP as HorusControlPlane participant LA as LocalAnvil participant LT as LocalTypesense participant LN as LocalNeo4j participant LG as LocalGit participant RG as RemoteGit U->>HCP: horus setup with JWT and deployment URL HCP->>HCP: validate JWT signature using deployment public key HCP->>HCP: write local config - deployment URL, JWT, user slug HCP->>LA: start local Docker stack: Anvil plus Typesense plus Neo4j plus git dir LA->>LT: initialize Typesense collection for user LA->>LN: initialize Neo4j database for user LA->>LG: initialize local git working directory LA->>RG: git remote add origin for Anvil sync repo RG-->>LA: remote configured LA-->>HCP: local Anvil stack healthy HCP-->>U: Local Anvil ready. MCP socket at localhost.
  1. Part A, Step 1 — Operator issues JWT. The operator runs horus user add --user alice. The CLI validates that the slug is DNS-safe (lowercase alphanumeric and hyphens only), then calls AuthLib.issueJWT with the user's slug and the deployment's tenant name from the config. A long-TTL JWT is produced.
  2. Part A, Step 2 — Out-of-band delivery. The operator delivers the JWT to Alice through a secure channel (password manager, encrypted email, etc.). Horus has no in-band delivery mechanism in Phase 1.
  3. Part B, Step 1 — User runs setup. Alice runs horus setup on her machine, providing the JWT and the deployment URL. The CLI validates the JWT signature using the deployment public key embedded in the JWT header.
  4. Part B, Step 2 — Write local config. The CLI writes a local config file containing the deployment URL, the JWT, and the resolved user slug. This file is used by subsequent CLI commands and by the local Anvil stack.
  5. Part B, Step 3 — Start local Docker stack. The CLI starts the local Anvil Docker stack: an Anvil MCP server process, a local Typesense instance, a local Neo4j instance, and a git working directory. All components run in Docker containers on Alice's machine.
  6. Part B, Step 4 — Initialize local stores. Anvil initializes a Typesense collection and a Neo4j database for the user, then sets up a git working directory for Anvil data.
  7. Part B, Step 5 — Connect to git remote. Anvil adds the user's private git remote (e.g. a private GitHub repo) as the origin for the Anvil sync repo. This remote is used for cross-device sync via push and pull.
  8. Part B, Step 6 — Ready. The local Anvil MCP socket is available at localhost. Claude Code and other clients can now connect to it.

Section 3 — Creating a Vault (Operator Only)

Vault creation and deletion are out-of-band operator actions. Users cannot create or delete vaults; they can only read and write within vaults that already exist. Each vault has its own git remote (declared in the deployment config), its own Typesense collection, and its own Neo4j database. VaultWriter does the initialization work; VaultReader becomes aware of the new vault once VaultRouter reloads its config.

sequenceDiagram participant Op as Operator participant HCP as HorusControlPlane participant VR as VaultRouter participant VW as VaultWriter participant TS as Typesense participant NJ as Neo4j participant RG as RemoteGit Op->>HCP: horus vault create engineering HCP->>RG: initialize empty git repo at declared remote URL for engineering vault RG-->>HCP: remote repo ready HCP->>HCP: add vault to deployment config - name, git remote URL, and vault ID HCP->>VW: notify config reload with new vault entry VW->>RG: git clone working copy of engineering vault into PVC RG-->>VW: working copy cloned VW->>TS: create per-vault Typesense collection horus_engineering TS-->>VW: collection created VW->>NJ: create per-vault Neo4j database engineering NJ-->>VW: database created VW-->>HCP: vault worker initialized and queue running HCP->>VR: notify config reload - engineering vault now known VR-->>HCP: VaultRouter updated known-vault list HCP-->>Op: Vault engineering is ready. Users can read and write immediately.
  1. Step 1 — Operator command. The operator runs horus vault create engineering. The vault name must match a git remote URL already declared in the deployment config.
  2. Step 2 — Initialize remote git repo. HorusControlPlane initializes an empty git repository at the declared remote URL. This is the authoritative git store for this vault's markdown files.
  3. Step 3 — Update deployment config. The vault entry (name, git remote URL, internal vault ID) is added to the deployment config on disk. This is the config that VaultRouter and VaultWriter will reload.
  4. Step 4 — VaultWriter clones working copy. After receiving a config reload signal, VaultWriter clones a working copy of the vault's git repo into its PVC (persistent volume). This is the working copy VaultWriter's queue workers will use to write files.
  5. Step 5 — Create Typesense collection. VaultWriter creates a per-vault Typesense collection (e.g. horus_engineering) with the standard page schema. All future reads will come from this collection — no separate file-fetch step.
  6. Step 6 — Create Neo4j database. VaultWriter creates a per-vault Neo4j database (e.g. engineering). Graph edges between pages will be stored here.
  7. Step 7 — Start vault worker. VaultWriter starts a per-vault in-process queue worker. This worker is the sole entity that commits to git and updates Typesense and Neo4j for this vault.
  8. Step 8 — VaultRouter config reload. VaultRouter reloads its known-vault list so that incoming requests for the engineering vault are now routable.
  9. Step 9 — Vault ready. The vault is immediately available for reads and writes by any user holding a valid JWT.
Note: After config reload, VaultReader replicas automatically learn the new vault because they route through VaultRouter. No per-replica restart is needed.

Section 4 — User Accessing Their Anvil Data (Entirely Local)

Anvil is entirely local in the locked alpha design. There is no AnvilRouter, no remote Anvil server, and no PrincipalStore involved. The Client (a Claude agent or CLI process) connects to LocalAnvil via a local MCP socket on localhost. All data operations hit LocalTypesense, LocalNeo4j, and LocalGit — all running in Docker containers on the same machine. No network call leaves the user's machine during normal Anvil use.

sequenceDiagram participant C as Client participant LA as LocalAnvil participant LT as LocalTypesense participant LN as LocalNeo4j participant LG as LocalGit C->>LA: MCP tool call via localhost socket - e.g. anvil_search or anvil_create_note Note over C,LA: No JWT check needed. Network reachability to
the local socket is the only auth gate.
Only processes on the same machine can connect. alt Search or list query LA->>LT: Typesense search or filter query LT-->>LA: matching documents with full body LA-->>C: MCP response with results else Create or update note LA->>LT: upsert document into Typesense LT-->>LA: ok LA->>LN: write or update graph edge LN-->>LA: ok LA->>LG: git commit with change and user slug as author LG-->>LA: committed LA-->>C: MCP response with updated note else Graph query - get related or get edges LA->>LN: Cypher query for edges or related nodes LN-->>LA: edge list or related node IDs LA->>LT: fetch documents by ID for each related node LT-->>LA: page bodies LA-->>C: MCP response with related pages end
  1. Step 1 — Client connects via local socket. The Client (Claude Code agent, CLI process) connects to LocalAnvil via a localhost MCP socket. There is no JWT check — the local socket is accessible only from the same machine, so network reachability is the auth gate.
  2. Step 2 — Search or list path. For read operations like anvil_search or anvil_list_by_scope, LocalAnvil queries LocalTypesense. Typesense stores full document bodies, so a single query returns complete results — no secondary fetch from disk.
  3. Step 3 — Create or update path. For write operations like anvil_create_note or anvil_update_note, LocalAnvil upserts the document into LocalTypesense, updates graph edges in LocalNeo4j if applicable, and commits the change to LocalGit with the user slug as the git author. All three writes happen in the same local transaction sequence.
  4. Step 4 — Graph query path. For operations like anvil_get_related or anvil_get_edges, LocalAnvil queries LocalNeo4j for the edge data, then fetches the referenced documents by ID from LocalTypesense to populate the response bodies.
  5. Step 5 — Response. LocalAnvil returns the MCP response to the Client. All of this happens without any network call leaving the user's machine.

Multi-device sync via git

When a user switches to a second machine (or wants to resume after a gap), they run horus setup or a sync command. LocalAnvil pulls the latest commits from RemoteGit and replays any new documents into LocalTypesense and LocalNeo4j to bring the local stores up to date.

sequenceDiagram participant U as User participant LA as LocalAnvil participant LT as LocalTypesense participant LN as LocalNeo4j participant LG as LocalGit participant RG as RemoteGit Note over U: User on machine B starts Horus or triggers sync U->>LA: horus sync or session start LA->>LG: git fetch origin LG->>RG: fetch commits since last sync RG-->>LG: new commits LG->>LG: git merge fast-forward LG-->>LA: list of changed files since last HEAD LA->>LT: upsert changed documents into Typesense LT-->>LA: ok LA->>LN: update graph edges for changed documents LN-->>LA: ok LA-->>U: Local stores in sync. Anvil MCP ready.
  1. Step 1 — Trigger sync. The user runs a sync command or Horus triggers sync at session start. This is a manual or semi-automatic operation in alpha — there is no continuous background sync.
  2. Step 2 — Git fetch and merge. LocalAnvil instructs LocalGit to fetch from RemoteGit and merge the new commits into the local working directory. Fast-forward merges are the expected case; conflict resolution is not automated in Phase 1.
  3. Step 3 — Replay into local stores. LocalAnvil reads the list of files changed since the last-known HEAD and upserts each changed document into LocalTypesense, then updates the corresponding Neo4j graph edges.
  4. Step 4 — Ready. The local Anvil stores are now consistent with the latest committed state. The MCP socket continues serving requests.

Section 5 — User Reading from Vault

The Vault read path is the highest-volume path in the system. VaultReader replicas are stateless — they hold no filesystem state and make no git calls. All reads go to Typesense (for document search and fetch) or Neo4j (for graph queries). Typesense stores the full page body, so there is no secondary file-fetch step. VaultRouter is the only network hop between the client and VaultReader; it also performs JWT verification via AuthLib. Any VaultReader replica can serve any read request.

sequenceDiagram participant C as Client participant VR as VaultRouter participant AL as AuthLib participant VRd as VaultReader participant TS as Typesense C->>VR: GET /vault/engineering/knowledge/search with Authorization Bearer token VR->>AL: verifyJWT with token alt JWT invalid or expired AL-->>VR: error VR-->>C: 401 Unauthorized else JWT valid AL-->>VR: claims with principal.user extracted for audit VR->>VR: locate vault engineering in known-vault list alt Vault not found in known-vault list VR-->>C: 404 vault not found else Vault found VR->>VRd: forward GET /knowledge/search to any VaultReader replica VRd->>TS: Typesense search query against horus_engineering collection TS-->>VRd: matching documents with full page body and metadata VRd-->>VR: search results VR-->>C: 200 with page results end end
  1. Step 1 — Client sends read request. The Client sends a GET request to VaultRouter with the vault name in the path and the JWT in the Authorization header.
  2. Step 2 — JWT verification. VaultRouter calls AuthLib.verifyJWT in-process. AuthLib checks the signature against the deployment public key and confirms the token is not expired. No network call to a central auth service.
  3. Step 3 — Invalid JWT path. If verification fails, VaultRouter returns 401 and does not contact VaultReader.
  4. Step 4 — Principal extraction. From the verified claims, VaultRouter extracts principal.user. This is used for audit logging only — there is no per-user access control list in alpha. Every valid JWT gives full access to every vault in the deployment.
  5. Step 5 — Vault routing. VaultRouter checks that the requested vault name appears in its known-vault list (loaded from deployment config). If not found, it returns 404.
  6. Step 6 — Forward to VaultReader. VaultRouter forwards the request to any available VaultReader replica (round-robin or least-connections). VaultReader is stateless, so any replica can serve any request.
  7. Step 7 — Typesense query. VaultReader queries the per-vault Typesense collection. Because Typesense stores the full page body, a single query returns everything the client needs. No secondary filesystem read is needed.
  8. Step 8 — Return results. VaultReader returns the result set to VaultRouter, which passes it back to the Client.
Typesense holds the full page body. There is no separate file-fetch step on the read path. The git working copy on VaultWriter's PVC is the authoritative source, but clients never read from it directly — Typesense is the read cache and it is always up to date because VaultWriter updates it synchronously on every write.

Graph query path (related pages and edges)

When the client issues a graph query such as fetching related pages or traversing edges, VaultReader queries Neo4j instead of Typesense for the structural data, then optionally fetches document bodies from Typesense for the referenced pages.

sequenceDiagram participant C as Client participant VR as VaultRouter participant AL as AuthLib participant VRd as VaultReader participant NJ as Neo4j participant TS as Typesense C->>VR: GET /vault/engineering/knowledge/related with page ID and Authorization Bearer token VR->>AL: verifyJWT with token AL-->>VR: claims valid VR->>VRd: forward graph query to VaultReader replica VRd->>NJ: Cypher query against engineering database for related page IDs NJ-->>VRd: list of related page IDs with edge types VRd->>TS: fetch documents by ID list from horus_engineering collection TS-->>VRd: page bodies for related pages VRd-->>VR: related pages with edge metadata VR-->>C: 200 with related pages
  1. Steps 1-3 — Auth and routing. Identical to the standard read path: JWT verified by AuthLib in-process, vault located in known-vault list, forwarded to VaultReader.
  2. Step 4 — Neo4j query. VaultReader issues a Cypher query against the per-vault Neo4j database to retrieve the IDs and edge types of pages related to the requested page.
  3. Step 5 — Typesense fetch by ID. VaultReader fetches the full document bodies for the related page IDs from Typesense. This is a batch fetch-by-ID operation, not a search query.
  4. Step 6 — Return. VaultReader combines the Neo4j edge metadata with the Typesense document bodies and returns the enriched result to the Client.

Section 6 — User Writing to Vault

All writes to a vault go through VaultWriter — the single replica that owns the per-vault in-process queue, the git working copies, and all mutations to Typesense and Neo4j. The queue serializes writes per vault to prevent concurrent git conflicts. VaultWriter performs an optimistic version check before writing; if the client is working from a stale version, it receives a 409 and must retry with the latest version.

sequenceDiagram participant C as Client participant VR as VaultRouter participant AL as AuthLib participant VW as VaultWriter participant TS as Typesense participant NJ as Neo4j participant LG as LocalGit participant RG as RemoteGit C->>VR: POST /vault/engineering/knowledge/pages with Authorization Bearer token and page body and expected version VR->>AL: verifyJWT with token alt JWT invalid AL-->>VR: error VR-->>C: 401 Unauthorized else JWT valid AL-->>VR: claims with principal.user for git author VR->>VW: forward POST to VaultWriter - only one replica exists VW->>VW: enqueue task on the engineering vault queue Note over VW: Queue ensures one writer at a time per vault.
Tasks processed in FIFO order. VW->>VW: vault worker picks up task VW->>VW: optimistic version check - sha256 of current file vs expected version in request alt Version mismatch - stale client VW-->>VR: 409 Conflict with current version VR-->>C: 409 Conflict - retry with latest version else Version matches or new page VW->>LG: write file to git working copy in PVC LG-->>VW: file written VW->>TS: upsert document with full body into horus_engineering collection TS-->>VW: ok VW->>NJ: update graph edges for this page in engineering database NJ-->>VW: ok VW->>LG: git commit with principal.user as author LG-->>VW: committed VW->>RG: git push to vault remote RG-->>VW: pushed VW-->>VR: 200 with new version sha256 VR-->>C: 200 with updated page and new version end end
  1. Step 1 — Client sends write request. The Client sends a POST or PUT to VaultRouter with the page body, the expected version (sha256 of the content the client last read), and the JWT.
  2. Step 2 — JWT verification. VaultRouter calls AuthLib.verifyJWT in-process. Invalid tokens return 401 immediately.
  3. Step 3 — Extract principal.user. VaultRouter extracts principal.user from the verified JWT claims. This value will be used as the git commit author, providing an audit trail of who made each change.
  4. Step 4 — Route to VaultWriter. VaultRouter forwards the write request to VaultWriter. There is exactly one VaultWriter replica — no load balancing is needed for writes.
  5. Step 5 — Enqueue task. VaultWriter enqueues the write task on the per-vault in-process queue for the engineering vault. The queue ensures that only one write executes at a time for this vault, preventing concurrent git conflicts.
  6. Step 6 — Vault worker picks up task. The per-vault queue worker dequeues the task and begins processing.
  7. Step 7 — Optimistic version check. The worker computes the sha256 of the current file content on disk and compares it to the expected version in the request. If they do not match, the client is working from a stale version.
  8. Step 8 — Version conflict path. If the version check fails, the worker returns 409 Conflict with the current version. The client must re-read the page, merge its changes, and retry the write.
  9. Step 9 — Write to git working copy. If the version check passes (or this is a new page), the worker writes the file to the git working copy on the PVC.
  10. Step 10 — Update Typesense. The worker upserts the full page body and metadata into the per-vault Typesense collection. After this point, read replicas will return the new content.
  11. Step 11 — Update Neo4j. If the page has link or edge changes, the worker updates the per-vault Neo4j database.
  12. Step 12 — Git commit and push. The worker commits the change with principal.user as the git commit author and pushes to the vault's remote git repo. This provides a durable, auditable history.
  13. Step 13 — Respond. VaultWriter returns 200 with the new version (sha256 of the written content). VaultRouter passes this back to the Client.
No caching layer exists in Phase 1. No batch write API exists in Phase 1. Each write goes through the queue individually.

Section 7 — User Creating Workspace Artifacts via Forge

Forge has two distinct layers. Workspaces are a local execution-plane concept: directories at ~/Horus/workspaces/name/ on the user's machine, created by the Horus CLI with no remote service calls. The Forge Registry is a service-plane concept: an S3-backed artifact store that the CLI contacts to resolve and download artifacts. Sessions (forge_develop) are local git worktrees, also separate from workspaces.

sequenceDiagram participant C as Client participant FR as ForgeRegistry participant S3 as S3 Note over C: forge_workspace_create runs locally.

C->>C: create workspace directory on local filesystem C->>C: write workspace config with mcp.json and skills list and permissions Note over C,FR: Installing an artifact from the registry C->>FR: GET resolve artifact by name horus-anvil at version latest FR->>FR: AuthStrategy check - read is anonymous in alpha FR-->>C: artifact metadata with resolved version and download URL C->>FR: GET download artifact horus-anvil at resolved version FR->>S3: getObject for artifact tarball from storage key S3-->>FR: artifact bytes FR-->>C: artifact stream C->>C: extract tarball and install artifact into workspace directory C-->>C: workspace ready with artifact installed
  1. Step 1 — Workspace creation (local only). forge_workspace_create creates a directory on the user's local filesystem at ~/Horus/workspaces/name/. It writes config files including mcp.json, a skills list, and permissions. This is a pure filesystem operation — no network call is made to any Horus service. Workspaces do NOT clone repositories.
  2. Step 2 — Artifact resolution. When the user adds an artifact, the CLI calls the ForgeRegistry resolve endpoint with the artifact name and desired version. ForgeRegistry returns the resolved version and a download URL.
  3. Step 3 — AuthStrategy check. ForgeRegistry evaluates the request through its AuthStrategy. In Phase 1, reads are anonymous — no JWT or API key is required to download an artifact. The admin key is only required to publish.
  4. Step 4 — S3 retrieval. ForgeRegistry fetches the artifact tarball from S3 using an internal storage key. Clients never interact with S3 directly.
  5. Step 5 — Install locally. The CLI extracts the tarball and installs the artifact into the workspace directory. The workspace is now ready to use with the artifact available.

Publishing an artifact

sequenceDiagram participant C as Client participant FR as ForgeRegistry participant S3 as S3 C->>FR: POST /publish with tarball and metadata and admin key in Authorization header FR->>FR: AuthStrategy check admin key alt Not authorized - missing or invalid admin key FR-->>C: 403 Forbidden else Authorized FR->>S3: putObject tarball at storage key artifacts-name-version S3-->>FR: etag confirmed FR->>FR: update registry index with name, version, sha256, and manifest entry FR-->>C: 201 Created with artifact download URL end
  1. Step 1 — Publish request. The publisher (operator or CI system) sends the artifact tarball and metadata to ForgeRegistry's publish endpoint, including an admin API key in the Authorization header.
  2. Step 2 — Authorization. ForgeRegistry's AuthStrategy checks the admin key. If absent or invalid, the request is rejected with 403. Anonymous callers cannot publish in any phase.
  3. Step 3 — S3 write. ForgeRegistry writes the tarball to S3 under a storage key structured as artifacts/name/version.tar.gz. Note: keys are not namespaced by tenant in Phase 1 — all tenants share the same S3 key namespace.
  4. Step 4 — Index update. ForgeRegistry updates its registry index with the artifact name, version, sha256 checksum, and manifest. Future resolve calls will find this version.
  5. Step 5 — Confirmation. A 201 response with the artifact download URL is returned to the publisher.
Tenant gap (post-alpha): S3 storage keys are not namespaced by tenant. All users sharing a ForgeRegistry deployment share the same artifact namespace. An admin key holder can overwrite any artifact at the same name and version regardless of who published it. True isolation requires either key-prefix scoping per tenant or separate S3 buckets per tenant. This is a known deferred item for post-alpha.

Section 9 — Open Questions for Later

  1. Local Anvil setup ergonomics. horus setup needs to start a Docker or Podman stack on the user's machine automatically. Questions include: how does the CLI detect whether Docker or Podman is available; how are port conflicts handled; how does the user know which MCP socket address to configure in Claude Code; and how is the Anvil stack updated when new default types ship. A guided setup wizard or a CLI doctor command would help surface these issues.
  2. Multi-device Anvil git sync UX. In the locked alpha, sync is manual — the user runs a sync command or it triggers at session start. There is no conflict resolution automation if two devices write to the same note concurrently. Questions to answer: should sync be automatic in the background; how should merge conflicts surface to the user; and should the system use git-level conflict markers or a higher-level CRDT approach for Anvil note content.
  3. Vault create and delete CLI surface. The current design positions vault creation as an operator-only out-of-band action, but the CLI surface for horus vault create and horus vault delete is not fully specified. Questions include: what happens to data in Typesense and Neo4j when a vault is deleted; how is the git remote archived or removed; and what is the rollback procedure if vault creation partially fails partway through the initialization sequence.
  4. S3 binary attachment support for Vault (next phase). The locked alpha stores only markdown-in-git. Binary file support (images, PDFs, attachments) requires S3 or equivalent object storage. Questions for the next phase: how are S3 references embedded in markdown; how does VaultReader serve binary blobs (presigned URLs vs. proxy); and whether the binary store is per-vault or shared with Forge Registry storage.
  5. Forge Registry tenant scoping (post-alpha). S3 keys are currently not namespaced by tenant, meaning all users sharing a ForgeRegistry instance share the artifact namespace. Questions for post-alpha: does Horus become a shared-registry SaaS (requiring key-prefix scoping or separate S3 buckets per tenant), or does each company deployment receive its own ForgeRegistry instance (natural isolation through separate buckets); and how does artifact versioning interact with tenant scoping if the same artifact name exists for multiple tenants.
