Horus · Local Client

Local Client — Setup & Run
New Architecture

Get the new split-architecture client running locally — operator-mediated onboarding, connected to the remote control plane.

Alpha CLI ≥ 0.8.2 New Architecture
Architecture in one line
🏗

Local containers — horus-ui (with embedded Forge exec engine) + anvil + typesense + neo4j — talking to a remote control plane (horus-service gateway) for auth (JWT) + routing to remote Vault and the remote Forge registry.

The split means your notes, graph, and agent execution live on your machine; discovery, publishing, and Vault knowledge live in the cloud. See the Architecture Showcase for the full picture.

Prerequisites

Before you start

  • ▸
    Docker (or Podman)

    The client runs as 4 containers. Docker Desktop or Docker Engine ≥ 24 recommended. Podman with Docker-compat socket works too.

  • ▸
    Node 20+

    Required to install and run the Horus CLI. Use node -v to verify.

  • ▸
    Horus CLI @arkhera30/cli ≥ 0.8.2

    Install or upgrade: npm i -g @arkhera30/cli@latest. Version 0.8.0 is broken — do not use it (see Version Notes below).

  • ▸
    kubectl access to the control-plane cluster

    For operator onboarding only. The operator CLI auto port-forwards to the operator-service (ClusterIP). Not required for end-users consuming a pre-minted bundle.

Onboarding modes

How you get started

🔑

Operator-mediated

Default for alpha and enterprise deployments. An operator mints a per-user config bundle via the Horus CLI. The user consumes it with horus setup --config <bundle>. No manual credential wrangling required.

Default — Alpha
🖥

Local-only (dev)

No control plane required. Skips auth, JWT, and remote routing. Useful for development or offline work. Run horus setup --local-only --yes to get started immediately.

Dev / offline
Step 1 — Operator

Operator mints a bundle

One-time, per user. The operator needs kubectl access; the operator-service is ClusterIP-only — the CLI auto port-forwards, or pass --operator-url to point at a manually forwarded endpoint.

01

Mint the user config bundle

Run as an operator — requires cluster access

Operator
bash 
# Operator (needs kubectl access; operator-service is ClusterIP-only —
# the CLI auto port-forwards, or pass --operator-url)
horus operator login                                  # first login rotates+stores the bootstrap-admin credential
horus operator user add <userId> \
  --tenant <tenant> \
  --cp-url https://horus.arjunkhera.io \
  --out <userId>.bundle.yaml                          # optionally: --vault <ns=endpoint> to assign a vault
What's in the bundle? It contains control_plane_url + a static principal JWT (token_provider.kind=static). Hand it to the user over a secure channel — it's a credential.
Step 2 — User

User sets up & runs the client

02

Install CLI, setup, and start

Run as the end-user on their local machine

User
bash 
npm i -g @arkhera30/cli@latest                        # >= 0.8.2
horus setup --config <userId>.bundle.yaml --yes       # provisions config + new compose, logs in
horus up                                              # pull GHCR images + start the 4 containers
horus connect                                         # wire Claude Code / Desktop / Cursor MCP
horus status                                          # check service health
What does setup --config do? It loads the bundle, writes ~/Horus/config.yaml + .env, generates the new 4-container compose (horus-ui, anvil, typesense, neo4j — Vault and the Forge registry are remote), and runs login with the static principal token from the bundle. GHCR images are public — no docker login needed.

Forge carve-out

What runs where

Forge is split across local and remote. Execution and workspace management are local; discovery and publishing are remote.

⚙

Forge — Local vs Remote split

Local — horus-ui · your machine
  • forge_develop
  • forge_workspace_create
  • forge_workspace_delete
  • forge_workspace_list
  • forge_workspace_status
  • forge_session_cleanup
  • forge_session_list
  • forge_add
  • forge_install

Git worktree creation + claude -p agent spawning run on your hardware. No data leaves the machine for these operations.

Remote — control plane via gateway
  • forge_search
  • forge_resolve
  • forge_publish
  • forge_repo_get
  • forge_repo_list
  • forge_repo_register
  • forge_repo_remove
  • forge_repo_resolve

Registry queries and publishing are handled by the remote Forge registry service, reached through the horus-service gateway (JWT required).

Troubleshooting

Common issues

Based on real end-to-end validation runs.

Symptom Cause Fix
npm install fails resolving @forge/core CLI 0.8.0 declared an unpublished internal package as a dependency — npm cannot resolve it. Use CLI ≥ 0.8.1. Run npm i -g @arkhera30/cli@latest.
anvil container restarts; log: ANVIL_REPO_URL is not set and /data/notes has no .git. Cannot start. Older anvil image required a pre-existing git-backed notes repository to start. Use anvil ≥ 0.8.2 (auto-inits a local-only notes repo). Workaround on older images: set ANVIL_REPO_URL env var, or git init the notes dir manually.
horus-ui shows "unhealthy" in docker ps even though /health returns 200 Older compose healthcheck used wget, which is absent from the node:22 image. Use CLI ≥ 0.8.2 — the compose template was updated to use curl instead.
GHCR image pull fails with auth error GHCR images are public; an old cached credential may interfere. Run docker logout ghcr.io to clear any stale credential. No login is needed for ghcr.io/arjunkhera/horus/*.
