01 — Architecture at a glance

Two planes, one coherent system

Your notes and code sessions never leave your machine. The shared knowledge base and artifact registry live in the always-on control plane, accessed over an authenticated gateway.

On your machine — Horus Local Client
horus-ui
The local backend: agent chat UI, MCP tool surface, and the embedded Forge local-execution engine — worktrees and agent spawn included.
anvil
Your personal notes, tasks, stories, and journals. Private, per-user, never synced to the cluster.
typesense
Local full-text and semantic search index — zero-latency queries, no network round-trip.
neo4j
Local knowledge graph — edges, relationships, and traversals over your own data.
HTTPS · JWT auth
routed by horus-service
Remote Control Plane — horus.arjunkhera.io
horus-service
Public API gateway: verifies your JWT, mints an internal X-Horus-Principal token, and routes /api/v1/vault/* and /api/v1/forge/*.
operator-service
Admin and provisioning: onboards users, provisions vaults, governs the request queue. Not publicly exposed.
Vault (remote)
Shared team knowledge base — guides, procedures, repo profiles — reached via vault-router.
Forge registry (remote)
The shared artifact catalog: 135+ skills, plugins, agents, personas. S3-backed, in-cluster.
02 — The Forge carve-out
⚙

Forge is split in two

Execution is irreducibly local. The catalog lives in the cluster.

Local — runs on your machine
  • forge_develop
  • forge_workspace_create / list / delete / status
  • forge_session_list / cleanup
  • forge_add
  • forge_install
  • git worktree creation
  • claude -p (agent spawn in worktree)

The coding agent is launched via claude -p with cwd set to the worktree — it auto-loads the repo's CLAUDE.md and skills, and inherits your Claude login. Your repos and code sessions never leave your machine.

Remote — control plane
  • forge_search
  • forge_resolve
  • forge_publish
  • forge_repo_register
  • forge_repo_get / update / remove / list / resolve

The shared artifact catalog lives in the cluster — 135+ artifacts (skills, plugins, agents, personas) stored in S3 and served from the in-cluster registry.

03 — What the local client can do

Six core capabilities

🗃

Own your knowledge & work

Create, search, and manage notes, tasks, stories, and journals in your local Anvil instance. Everything is instant and private — no network dependency, no shared state.

🔍

Search everything locally

Full-text and semantic search via Typesense plus graph traversal via Neo4j — sub-millisecond queries over your entire personal knowledge graph without a network round-trip.

🛠

Spin up isolated coding sessions

forge_develop({ repo, workItem }) creates a git worktree on your machine and launches a Claude agent inside it. The agent auto-loads the repo's CLAUDE.md and installed skills.

⚡

Run headless

horus run --workspace <id> --story <id> executes the same agent flow non-interactively with the Anvil story spec preloaded — ideal for CI pipelines and automated SDLC loops.

📦

Install shared tooling

Browse the remote Forge registry with forge_search, then pull artifacts to your local machine with forge_add and forge_install — no manual file management.

📚

Use shared team knowledge

Read and write the remote Vault — guides, procedures, repo profiles — through the horus-service gateway. Single sign-on via JWT; no separate credential per service.

04 — Onboarding (operator-mediated, alpha)

Three steps from zero to connected

1
Operator
horus operator user add

Mints a client token and writes a self-contained <user>.bundle.yaml with all connection parameters and credentials for the new tenant.

→
2
User
horus setup --config <user>.bundle.yaml

Consumes the bundle: writes config and .env, generates the local compose topology (horus-ui + anvil + typesense + neo4j), and starts the client.

→
3
User
horus login

Authenticates against the control plane. The local client is now wired to the remote Vault and the Forge shared registry. You're live.
