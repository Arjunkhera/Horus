Horus Platform Alpha

Kubernetes Infrastructure Topology — Namespace horus — Single tenant per deployment — Locked decisions as of 2026-05-25

Introduction

This document describes the locked alpha topology for a Horus cluster deployment. The shape is deliberately minimal: one cluster, one namespace, one tenant. The cluster runs three products — Vault, Forge, and Control Plane. It does not run Anvil.

Anvil is a local-first system. Every user runs Anvil on their own machine inside Docker or Podman, pointed at a local Typesense and Neo4j. The cluster has no anvil-router, no anvil-backend, and no Anvil-specific storage. This is a fundamental architectural shift from the previous topology.

Within the cluster, the Vault service is split into two separate workloads: a stateless Reader pool (2–3 replicas, autoscaling) and a single-replica Writer that owns all per-vault git working copies. This split enables horizontal read scaling without touching the write path, while preserving the serialization guarantees that vault git history requires.

Typesense and Neo4j are shared singletons. Logical per-vault isolation is enforced by naming convention: Typesense collection vault_<name>, Neo4j database vault_<name>. There is no per-tenant routing logic and no PrincipalStore.

Read path — no git, no PVC dependency

flowchart LR EC2["External Client"] GW2["horus-gateway"] SvcW["vault-writer Service"] VW["vault-writer pod"] PVC["PVC git working copies"] TS2["Typesense"] NEO2["Neo4j"] RG["Remote Git"] EC2 -->|"write request"| GW2 GW2 -->|"routes write"| SvcW SvcW --> VW VW -->|"file write"| PVC VW -->|"index update"| TS2 VW -->|"graph write"| NEO2 VW -->|"git push"| RG

Write path — serialized through single writer replica

The read path has zero stateful dependencies on git. Readers query Typesense and Neo4j directly. The writer owns all per-vault git working copies on its PVC and is the only process that performs git operations. The single-replica constraint on vault-writer is deliberate: concurrent git writers would corrupt history.

Recommended instance: AWS m5.2xlarge — 8 vCPU, 32 GB RAM — approximately $240/month on-demand. With a 1-year Compute Savings Plan the effective rate drops to roughly $155/month. Total cluster cost including EBS storage and data transfer is under $300/month for the alpha. Sizing is validated for 50 vaults, 1000 pages each, at read-heavy load.

Scaling Triggers

Signal Action
Reader CPU sustained above 70% HPA adds vault-reader replicas (up to 10). No config change needed.
Read latency rises despite added replicas Profile Typesense query time. Add reader replicas first, then consider Typesense read replicas if queries saturate.
Typesense memory saturates (approaching 3 GB limit) Increase container memory limit, then evaluate Typesense cluster mode (3-node Raft) for horizontal scale-out.
vault-writer queue contention visible or SPOF unacceptable Introduce a durable queue (e.g. NATS or Redis Streams) in front of vault-writer, and an ownership registry to track which writer holds a vault lock. This allows multiple writer replicas with per-vault serialization.
Neo4j memory saturates Increase heap and page-cache limits. Neo4j HA requires Enterprise Edition causal clustering — deferred to post-alpha.
vault-writer PVC approaches 5 GB Resize EBS volume (online resize supported on gp3). Audit vault counts and prune stale remotes.
Gateway pod CPU or memory saturates Gateway is stateless — scale the Deployment to 2 replicas. Both containers (control-plane and vault-router) scale together.
Single-node cluster risk intolerable for production Move to a managed Kubernetes cluster (EKS) with node autoscaling and zone distribution. Wire up pod disruption budgets for gateway and reader.

What This Topology Does Not Include

Omission Rationale / Future phase
Anvil in the cluster (any form) Anvil is local-first. It runs on each user's machine. The cluster has no Anvil presence and never will under the current architecture.
PrincipalStore Deferred. Single tenant per deployment eliminates the need for cross-tenant identity lookup in alpha.
SaaS multi-tenant infrastructure Deferred. One cluster per customer/team is the alpha deployment model. Multi-tenancy across a shared cluster is a later phase.
HA for Typesense, Neo4j, or vault-writer All three are single replicas. Typesense HA requires Raft clustering; Neo4j HA requires Enterprise Edition. Writer HA requires a durable queue. All deferred post-alpha.
S3 for vault binary/media storage Deferred to the next phase. Vault currently stores everything in git on the writer PVC.
Cross-region replication Not modelled. Single-region deployment is sufficient for alpha.
Service mesh or mTLS between pods Not modelled. Internal cluster traffic is trusted in alpha. mTLS (e.g. via Istio or Linkerd) is a post-alpha hardening step.

What Changed from the Previous Topology

Change type Detail
Removed anvil-router container from the gateway pod. The gateway now contains only control-plane and vault-router.
Removed anvil-backend StatefulSet and all associated Services, PVCs, and Secret mounts. Anvil is entirely local.
Removed vault-backend StatefulSet (the old per-vault pod model). Replaced by the reader/writer split.
Added vault-reader Deployment: stateless, 2–3 replicas, autoscaling on CPU, no PVC.
Added vault-writer Deployment: single replica, owns the git working copies PVC, is the only workload that git-pushes.
Added Secret: horus-git-creds — new Secret consumed only by vault-writer for git push authentication.
Changed vault-router now differentiates read vs write traffic and routes them to separate Services (vault-reader vs vault-writer). Previously all vault traffic went to a single backend pool.
Resolved: pod-per-user question Moot. Anvil is local; there are no per-user pods in the cluster.
Resolved: shared vs per-service Typesense/Neo4j Confirmed shared singletons with per-vault logical isolation via naming convention.
Resolved: routers co-located Confirmed co-located in gateway pod. Only two containers now: control-plane and vault-router.
