Sample Kubernetes Deployment Topology — Namespace horus — Single cluster, single company

Introduction

This is a sample alpha topology, deliberately simple: one cluster, one company, every component at minimum viable replica count. The primary goal is to make the object inventory and traffic boundaries explicit so that later design forks can be evaluated against a concrete baseline. Per-component choices — gateway co-location, pod-per-user vs multi-tenant backends, HA strategy — are all open; the rationale for each current choice and its leading alternative is catalogued in Section 5.

Open Design Forks

  • 1. Pod-per-user vs multi-tenant Anvil backend

    Current One anvil-backend pod per (tenant, user) pair. The gateway registry maps (tenant, user) → ClusterIP DNS name deterministically, matching Track A's routing contract. Each pod gets its own resource limits and PVC; a crashed pod affects only one user.

    Alternative A single multi-tenant anvil-backend Deployment, isolating users via Typesense collection naming (anvil_<tenant>_<user>) and Neo4j database naming. This collapses N pods to 1–3, trivialises the gateway registry, and dramatically reduces K8s object count — but increases blast radius, eliminates per-user resource limits, and requires application-level multi-tenancy to be bulletproof.

  • 2. Routers co-located in gateway pod vs separate Deployments

    Current control-plane, anvil-router, and vault-router share one pod. They scale together as a single unit; inter-container communication is localhost with no network hop.

    Alternative Deploy each router as an independent Deployment. This allows independent horizontal scaling (e.g., vault traffic spikes without scaling anvil-router) and independent rollouts, at the cost of extra Services, inter-pod latency, and more YAML surface area.

  • 3. Shared vs per-service Typesense and Neo4j

    Current One typesense StatefulSet and one neo4j StatefulSet shared by all backends. Logical isolation is enforced via naming conventions: Typesense collection anvil_<tenant>_<user>, Neo4j database anvil-<tenant>-<user>.

    Alternative Separate Typesense or Neo4j instances per backend group (or even per tenant). Stronger isolation and independent tuning, but multiplies infra cost and operational complexity. The Horus vision document explicitly marks this as open.

  • 4. StatefulSet vs Deployment+PVC for backends

    Current StatefulSet for anvil-backend and vault-backend. StatefulSets provide stable, predictable pod DNS names (anvil-backend-0.anvil-backend.horus.svc.cluster.local), which is what the gateway's (tenant, user) → URL registry relies on. PVCs are automatically bound per-ordinal by the StatefulSet VolumeClaimTemplate.

    Alternative Deployment + manually managed PVCs + a sidecar or init-container that binds the correct PVC at runtime. This unlocks the Deployment's rescheduling flexibility, but requires custom pod-identity logic to recreate what StatefulSets provide for free.

  • 5. No HA in alpha (known limitation)

    Current horus-gateway, typesense, and neo4j are all single-replica. Any pod restart causes a brief outage for all users.

    Roadmap gateway scales horizontally (stateless). Typesense HA requires its Raft-based clustering mode (3-node minimum). Neo4j HA requires Enterprise Edition causal clustering. Both are deferred to post-alpha given their cost and complexity.

What This Does NOT Show

The execution plane — user workspaces and Forge code sessions — runs on user machines (or user-provisioned compute), not in this cluster. Each user's Claude Code instance connects to horus-gateway over the public Ingress; the gateway then fans out to the appropriate backend pod. Forge sessions (git worktrees) are local to the user's machine and managed by the Forge MCP server running there. Additionally, SaaS multi-cluster federation, cross-region replication, and any form of multi-cluster service mesh are explicitly post-alpha concerns and are not modelled here.
