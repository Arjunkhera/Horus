Vault Flat-UUID Storage Schema

From path-hierarchy pages → flat, UUID-keyed pages where search + graph are the only navigation.
The one idea: a page's identity is its UUID, and nothing else. The file path (pages/<uuid>.md) is a pure storage detail. You never navigate by folder — Typesense answers "which pages match?" and Neo4j answers "what's linked to this page?", both keyed by UUID. The old shared/ / concepts/ / repos/ hierarchy and the shared/ id-prefix disappear.

1 · The model: three stores over one git source of truth

A vault is a git repo (the bytes / source of truth) projected into two read-optimised indexes. Writes go to git; the indexes are rebuilt from git. Reads go to the indexes.

Crucially, all page metadata already lives in frontmatter — type, scope, title, tags are read from the file, never inferred from the folder. That's why flattening the hierarchy loses nothing.

2 · Why the shared/ prefix goes away

Today a doc id looks like shared/repos/horus.md. The shared/ part is a legacy single-vault artifact: one process used to serve two backends at once (shared/ = the knowledge repo, workspace/ = a locally-synced store), and the prefix told the code which filesystem root to read.

In multi-vault, the vault is the namespace — each vault has its own Typesense collection, its own git repo, its own Neo4j scoping. The router picks the collection before any read, so encoding it in the id is redundant. → doc id becomes the bare UUID.

4 · How it's indexed in Typesense

The Vault walks pages/*.md, reads frontmatter, and upserts one document per page. In the new schema the document id is the UUID; every other field still comes from frontmatter.

before · id = path 
{
  "id": "shared/repos/horus.md",
  "page_uuid": "0a9e1b34-…-1b2c3d4e5f60",
  "source": "vault",
  "source_type": "repo-profile",
  "title": "Horus Repository",
  "scope_repo": "horus",
  "vault_name": "default"
}
after · id = uuid 
{
  "id": "0a9e1b34-…-1b2c3d4e5f60",   // ← the uuid
  "source": "vault",
  "source_type": "repo-profile",
  "title": "Horus Repository",
  "body": "One product, one repo. Anvil, Forge and
           Vault are packages in this pnpm
           monorepo. They share the git repo,
           Typesense and Neo4j … <entire page>",  // full body, indexed
  "scope_repo": "horus",
  "scope_program": "horus",
  "tags": ["monorepo","architecture"],
  "vault_name": "default"
}
page_uuid as a separate field becomes redundant — it is the id now. Collection selection (horus_documents) is decided by vault routing, so it's no longer smuggled into the id string.
Full-body indexing. The body field holds the entire markdown, not just metadata or a snippet. Today it's truncated at BODY_MAX_CHARS = 20_000 (typesense_engine.py:123) — the new schema drops that cap so search covers the whole page. The short [:200] slices in the engine are only for result snippets and are unaffected.

A search → fetch round-trip

query: "package architecture"
→
Typesense returns 1b2c3d4e…
→
read pages/1b2c3d4e….md

No path lookup table, no directory walk — the hit is the UUID, and the file is at pages/<uuid>.md.

5 · How linking works in Neo4j

Every page is a :Page node keyed by page_id = uuid and scoped by vault_name. Cross-page references in frontmatter (related: [uuid]) become typed edges. The graph is already UUID-keyed today — flattening the files doesn't change it, except the stored key is the clean UUID instead of a path.

Writing the edges (frontmatter → graph)

// guide frontmatter:  related: [1b2c3d4e…, 0a9e1b34…]
// each related uuid is MERGEd as a :REFERENCES edge, scoped by vault
MERGE (s:Page {page_id: "2c3d4e5f-…-3f4051627384", vault_name: "default"})
MERGE (t:Page {page_id: "1b2c3d4e-…-2e3f40516273", vault_name: "default"})
MERGE (s)-[:REFERENCES]->(t);

Traversing — "what does the guide link to?"

MATCH (s:Page {page_id: "2c3d4e5f-…-3f4051627384", vault_name: "default"})
      -[:REFERENCES]->(t:Page)
RETURN t.page_id, t.title;

// → 1b2c3d4e…  "Horus Package Architecture"
// → 0a9e1b34…  "Horus Repository"

The returned page_ids are UUIDs — feed them straight back to pages/<uuid>.md or to a Typesense get. Identity is uniform across all three stores.

6 · Search experience — borrowed from Anvil

Anvil runs locally (per user); Vault runs remote (in the cluster). They no longer share a Typesense collection or a Neo4j — each owns its own. The win isn't a shared store, it's a shared pattern: the same @horus/search schema, the same UUID identity, and the same linking model — so mental model, skills and code carry across both systems. Two of Anvil's graph patterns drop straight into Vault's search-driven model now; semantic search comes in a later phase.

6.1 · Body wiki-links → a self-populating graph + backlinks

Anvil scans every body for [[…]] and auto-creates edges (indexer.ts:140, wiki-links.ts). Vault today only reads the frontmatter related list, so prose mentions create no links. Borrowing this, the graph builds itself from content — and every page gets backlinks for free.

page body (the guide) 
# pages/2c3d4e5f-…-3f4051627384.md  (body)
…for the call graph see
[[1b2c3d4e-…-2e3f40516273]],
and [[Horus Repository]] for the
package list.
on write → auto-edges 
// [[uuid]]  → direct registry lookup
// [[Title]] → resolve via search()
(guide)-[:MENTIONS]->(concept)
(guide)-[:MENTIONS]->(repo-profile)
// no manual `related:` curation needed

6.2 · Typed, inverse-labelled edges → real backlinks

Anvil's IntentRegistry gives every edge a direction and an inverseLabel, so a read from either end is correctly labelled. Vault's current get_edges returns target_id for both directions and loses the source of incoming edges — it can't say "referenced by." Borrowing the inverse-label idea:

references  ⇄  referenced_by      // directional pair
mentions    ⇄  mentions            // bidirectional
parent_of   ⇄  child_of

6.3 · Hybrid semantic + keyword deferred — later phase

Not in this pass. Captured here so the schema leaves room for it. Anvil wires HORUS_EMBEDDING_API_KEY → an embedding field and queries title,body,embedding; Vault's semantic_search/hybrid_search are stubs that fall back to BM25 (typesense_engine.py:271). When we pick this up, Vault adds embedding to query_by on its own collection.

8 · What actually changes in code

Because metadata is frontmatter-derived, the surface is small:

  • Write path — routes.py :: _write_page_sync: compute path = "pages/" + frontmatter.id + ".md" (drop hierarchy + the shared/ prefix), branch name derived from the UUID.
  • Typesense doc build — typesense_engine.py :: _build_document: set id = frontmatter.id (was the path); drop the now-redundant page_uuid field; stop inferring collection from id.split("/"); index the full body — drop the BODY_MAX_CHARS = 20_000 truncation at line 123 (keep the [:200] snippet slices, those are display-only).
  • UUID registry — simplifies to a thin uuid → pages/<uuid>.md mapping (or drops out where callers already pass UUIDs).
  • Reindex / discovery — already rglob("*.md"); works unchanged on the flat layout.
  • Data migration — one-shot: git mv each page to pages/<uuid>.md, rebuild Typesense, re-point Neo4j page_ids.
Pre-flight gate before migrating: every page must have id, title, type, scope in frontmatter, no path-based entries left in related, and no UUID collisions. (Title matters: a fallback path exists that would otherwise display the UUID.)
