# ADR-0008: Principal normalization at the gateway; two-key JWT model; X-Horus-Principal

**Status:** accepted
**Date:** 2026-05-28
**Related:** ADR-0003 (pluggable CredentialProvider/Verifier — this ADR extends it), ADR-0006
(Global→Tenant→User scope chain — Principal shape), ADR-0004 (layered control plane),
ADR-0007 (deployment); conversation-state `03619fa6` (Horus Phase 2 design, Sections E + H).

## Context

ADR-0003 locked the `Principal {tenant, user, role}` contract and the pluggable
CredentialProvider/Verifier plug pattern (SaaS reference: gateway signs an asymmetric JWT,
subsystems verify via JWKS). It explicitly **deferred** two things: (1) the specific header used to
forward the Principal to subsystems, and (2) **how the gateway itself is protected** (the
client→gateway credential).

Phase 2 needed to fill both holes concretely, and to handle a case ADR-0003 did not address: the
**client token may be in an enterprise-defined format** (via a pluggable TokenProvider/Verifier),
yet backends must never have to understand that format. The survey of existing services confirmed
Vault is wide-open (greenfield principal plumbing) and Forge has a `trusted-headers` strategy with
optional JWT verification — i.e. a header-carried, signature-verifiable principal is feasible today.

## Decision

**The gateway normalizes any client token into one canonical, internally-signed
`X-Horus-Principal` JWT. Two distinct keys separate client-facing auth from internal trust.**

1. **Normalization at horus-service.** On each request horus-service: (a) verifies the inbound
   `Authorization` token via the pluggable **TokenVerifier** → a `Principal`; (b) mints a fresh
   **internal JWT**; (c) injects it as **`X-Horus-Principal`** to backends, **replacing** the raw
   `Authorization`. Backends therefore only ever see one Horus-controlled token shape, regardless of
   the client token's format (Horus-native or enterprise).

2. **Two-key model** (fills ADR-0003's deferred "how the gateway is protected"):
   - **Client-facing key** — used by the pluggable TokenVerifier to validate what the client sends.
     May be Horus-native or enterprise-format (HTTP verify endpoint).
   - **Internal signing key** — horus-service **signs** `X-Horus-Principal`; Vault and Forge
     **verify** it via the public half (distributed as a K8s Secret). Both keys are generated by
     operator-service on first boot (per ADR-0007 bootstrap).

3. **`X-Horus-Principal` is a signed JWT, verified by signature — not merely presence.** Backends
   reject requests that are missing it **or** whose signature does not validate. Signature
   verification + NetworkPolicy = defense in depth (an in-cluster pod cannot forge a principal).

4. **Canonical Principal stays `{tenant, user, role}`** (per ADR-0003/0006). The internal JWT MAY
   additionally carry **`roles[]`** (a superset of `role`, for future multi-role grants) and a
   **`claims{}`** extension bag. These are **documented additive extensions**; they do not change
   the core contract, and alpha business logic binds to `{tenant, user, role}`.

5. **Internal JWT lifetime = 60s, minted per request-batch**, with **30s clock-skew leeway** on
   `exp`/`nbf`. Tight blast radius; no internal revocation machinery needed. The same 30s leeway
   applies to client→gateway token verification.

6. **TokenVerifier interface** (config-selected via `TOKEN_VERIFIER_KIND`):
   `verify(token) → { valid, principal {tenant, user, role, roles?[], claims?{}}, expiresAt }`.
   Default = in-process Horus-JWT verify; enterprise = HTTP call to a company verify endpoint,
   **cached until `expiresAt`**.

7. **Verify-endpoint failure fails CLOSED, with cache absorbing transient blips.** If the enterprise
   verify endpoint is unreachable and the token is not in the verified-cache, reject (401/503).
   Already-verified tokens keep working until their cached `expiresAt`, so a transient outage does
   not break active sessions — only brand-new tokens fail during the outage. Unverified principals
   are never admitted.

## Alternatives Considered

- **Single key for both planes** (reuse the client JWT key to sign `X-Horus-Principal`). Rejected —
  couples internal trust to the client token format and breaks normalization when the client uses an
  enterprise format.
- **Re-inject the raw client token to backends** (anvil-router's current behavior). Rejected — makes
  every backend depend on the TokenVerifier plumbing and the client token format; contradicts the
  one-canonical-principal goal.
- **Plain (unsigned) `X-Horus-Principal` JSON header, trusting network isolation only.** Rejected —
  any in-cluster pod could forge it; signature verification is cheap defense in depth.
- **Long-lived internal token mirroring the client token's expiry.** Rejected — larger leak window;
  60s + git-reverted key rotation is sufficient for alpha.
- **Fail-open on verify-endpoint outage.** Rejected — admits potentially-invalid principals on the
  privileged path.

## Consequences

### Positive
- Backends are decoupled from client token formats — enterprise integration is a horus-service
  concern only. Vault's greenfield middleware and Forge's `trusted-headers`+JWT both verify the same
  canonical token.
- Defense in depth: signature + NetworkPolicy, not network isolation alone.
- Tight 60s internal tokens make internal revocation unnecessary for alpha.

### Negative
- Two keys to generate, store (K8s Secret), and eventually rotate (rotation deferred — E-class).
- Per-request internal-JWT signing adds (negligible) CPU at the gateway.
- Clock-skew leeway (30s) plus 60s TTL means an internal token is honored for up to ~90s.

### Neutral
- Extends ADR-0003 without superseding it; the `Principal` shape and the provider/verifier plug
  pattern are unchanged. The `roles[]`/`claims{}` extensions are forward-compatible.
- Active token **revocation** (a `tokens` table for the Horus-default verifier) and **key rotation**
  remain **deferred** (post-alpha); `horus logout` is client-side discard in alpha.
